# Project Manager System 设计问题分析与改进方向

> 基于架构文档 v1.3.0 的深度评审
> 评审日期: 2026-06-12

---

## 概述

当前架构（v1.3.0）是一个面向**家庭服务器 / 内网场景**的多 Agent 协作项目管理系统，整体思路清晰：
- MCP 统一接入，角色隔离
- 工作流驱动协作
- SQLite + WAL 轻量部署
- 前端 React + SSE 实时推送

但在**安全、可靠性、扩展性**三个维度存在比较明显的设计债务。随着 Agent 数量增加和功能迭代，这些债务会指数级放大。

本文档从 7 个维度逐层剖析问题，并给出可落地的改进方向。

---

## 一、安全问题（P0 — 最高优先级）

### 1.1 MCP 密码通过 HTTP Header 明文传输

**现状**（文档 5.3 / 5.4）：
- MCP 使用 `X-PM-Password` Header 传递密码，传输层为 **HTTP**（非 HTTPS）。
- 即使在内网 / Tailscale 场景，Tailscale 提供的是**网络层加密**，但应用层明文密码仍存在风险：
  - 任何能抓包内网的设备（包括其他 Agent、智能家居设备）可直接读取密码。
  - 日志系统、反向代理、Nginx 访问日志可能意外记录 Header。

**改进方向**：
1. **强制启用 TLS**：使用 HTTPS 传输，或基于 Tailscale 的 TLS 证书终止。
2. **短期 Token 机制**：后端预生成短期 JWT，Agent 通过安全通道获取后写入 MCP 配置，避免长期密码暴露。
3. **挑战-响应签名**：若必须保留密码认证，Header 至少应做 HMAC-SHA256 签名，避免明文传输。

---

### 1.2 前端 localStorage 存储 JWT Token 与角色

**现状**（文档 4.2 / 4.4）：
- `token / sub / role / currentProject` 存储在 `localStorage`。
- 存在 **XSS 攻击面**：一旦前端出现注入漏洞，攻击脚本可直接读取 Token 并冒充用户。

**改进方向**：
1. **httpOnly Cookie**：Access Token 改为 httpOnly Cookie（`SameSite=Strict` + `Secure`），减少 XSS 风险。
2. **双 Token 策略**：Access Token 短期（15 分钟）+ Refresh Token 轮转（7 天），配合后端黑名单机制。
3. **敏感配置隔离**：`pm_global_resources` 等敏感数据避免 localStorage，改用 IndexedDB 加密存储或纯内存缓存。

---

### 1.3 环境变量集中管理多角色密码

**现状**（文档 7.2）：
- `AGENT_PASSWORDS_JSON` 将多个角色的 bcrypt 哈希放在单个环境变量。
- 运维困难，且一旦泄露则全部凭证暴露。

**改进方向**：
1. **按角色独立的 Secret 文件**：使用 Docker Secrets / Kubernetes Secrets / 外部 Vault（如 HashiCorp Vault）。
2. **运行时动态加载**：支持热更新密码，无需重启服务即可轮换凭证。
3. **密码版本化**：保留旧密码 24 小时兼容期，实现零停机轮换。

## 二、数据库与持久化问题（P0 / P1）

### 2.1 SQLite 作为生产数据库的隐性天花板

**现状**（文档 3.1 / 8.2）：
- 使用 SQLite + WAL 模式，配置 `pool_size=5, max_overflow=10`。
- 在家庭服务器场景下可用，但存在以下问题：
  - **并发写入瓶颈**：WAL 支持"多读单写"，但高并发写入时仍会锁竞争。
  - **缺乏运维工具**：无备份、PITR（时间点恢复）、主从复制方案。
  - **数据增长风险**：Agent 高频产生 Issue/Comment/ActivityLog，单文件体积可能迅速膨胀。
  - **连接池参数误导**：`pool_timeout=30` 和 `pool_recycle=3600` 对 SQLite 意义有限，可能掩盖连接泄漏。

**改进方向**：
1. **短期（保留 SQLite）**：
   - 增加自动备份策略（每日冷备份到另一个卷）。
   - 限制 WAL 文件大小（`wal_autocheckpoint=1000`）。
   - 定期 `VACUUM` 和 `ANALYZE` 维护。
2. **中期（提供 PostgreSQL 适配层）**：
   - 通过 SQLAlchemy 多绑定支持，SQLite 作为"轻量模式"，PostgreSQL 作为"生产模式"。
   - 提供一键迁移脚本（`sqlite → pg`）。
3. **长期**：当 Agent 数量 > 5 或日 Issue 量 > 500 时，建议强制迁移到 PostgreSQL。

---

### 2.2 消息队列的可靠性不足

**现状**（文档 3.5 / 8.3）：
- 基于 `asyncio.Queue(maxsize=1000)` + SQLite 备份。
- 这不是真正的消息队列：
  - **容量太小**：1000 条在 Agent 高频协作时容易被填满。
  - **无消费确认**：后台消费者"持续处理"，但没有 ACK 机制，失败消息可能丢失或无限重试。
  - **无死信队列**：消息一直失败会阻塞后续消息。
  - **重启丢数据**：backend 进程崩溃时，内存队列中的消息全部丢失（备份时机是"内存满时"，存在窗口期）。

**改进方向**：
1. **短期**：将内存队列改为 **SQLite 持久化队列**（写入即落盘，内存仅做缓存），增加消费确认和最多 3 次重试。
2. **中期**：引入 **Redis Streams** 或 **RabbitMQ** 作为可选消息后端，内存队列作为降级策略（Graceful Degradation）。
3. **长期**：如果部署到 K8s，使用外部消息服务（如 NATS / Kafka）。

## 三、工作流引擎问题（P0 / P1）

### 3.1 工作流状态未持久化

**现状**（文档 3.5）：
- WorkflowEngine 支持条件分支、并行执行，但**未明确 WorkflowRun 的持久化机制**。
- 如果 backend 重启：
  - 所有运行中的 `WorkflowRun` 状态丢失。
  - Agent 正在执行的异步任务（如 `wait_approval`）会中断且无法恢复。

**改进方向**：
1. **实时状态持久化**：工作流每一步状态变更必须**实时写入数据库**（SQLite / PG），backend 重启后自动扫描并恢复未完成的 WorkflowRun。
2. **幂等性设计**：每个工作流步骤生成唯一 `execution_id`，重复执行时先查状态再决定跳过或继续。
3. **断点续传**：支持从最后成功步骤恢复，而非从头重跑。

---

### 3.2 超时策略过于简单

**现状**（文档 3.5）：
- "5 分钟无进展自动 failed" 对所有步骤一刀切。
- 例如 `wait_approval` 可能需要几小时，`create_issue` 只需几秒。

**改进方向**：
1. **步骤级超时配置**：在 `WorkflowStep` 中增加 `timeout_seconds` 字段，按步骤类型配置超时。
2. **支持全局默认 + 步骤级覆盖**：`wait_approval` 默认 24 小时，`create_issue` 默认 30 秒。
3. **超时动作可配置**：超时后可选 `notify_human`、`skip`、`retry`、`abort`。

## 四、MCP 架构问题（P1）

### 4.1 统一端口 + 密码区隔角色的安全隐患

**现状**（文档 5.2 / 5.3）：
- 所有角色通过 `9000` 统一端口接入，仅通过密码区分角色。
- 风险：
  - 某个 Agent 密码泄露，攻击者可直接获得对应角色权限。
  - 没有**身份绑定**（如 IDE 指纹、证书），任何知道密码的客户端都能接入。
  - 单端口单进程，无法按角色做网络隔离。

**改进方向**：
1. **网络层隔离**：按角色分端口或子路径（如 `/mcp/agent`、`/mcp/mate`），配合防火墙规则限制 IP 白名单。
2. **引入 mTLS**：为每个角色颁发独立客户端证书，MCP Server 验证证书 CN 字段映射角色，即使密码泄露也无法连接。
3. **审计增强**：记录每个 MCP 连接的源 IP、IDE 标识、操作日志，异常连接自动熔断（如 5 分钟内 10 次失败则封禁 1 小时）。

---

### 4.2 MCP Server 缺乏水平扩展能力

**现状**（文档 5.1）：
- 123 行的统一入口 + 模块化工具，但仍然是**单进程**。
- 多个 Cursor/Trae 同时高频调用时可能成为瓶颈。

**改进方向**：
1. **多进程部署**：支持 Gunicorn + Uvicorn workers，或迁移到支持多 worker 的 MCP 传输方案。
2. **请求队列与限流**：增加 Rate Limiting（如单个 Agent 每分钟最多 200 次调用），防止单个 Agent 刷爆服务。
3. **负载均衡**：在 MCP 前端增加 Nginx 反向代理，支持多实例负载均衡。

---

## 五、前端与 API 设计问题（P1 / P2）

### 5.1 SSE + 30 秒轮询的双重推送

**现状**（文档 4.4）：
- 通知同时使用 SSE 实时推送和 30 秒轮询。
- 逻辑冗余，增加服务端负载。

**改进方向**：
1. **SSE 为主，轮询为降级**：以 SSE 为主推送通道，轮询仅在 SSE 断开时触发（Exponential Backoff 重连 SSE，而非固定 30 秒轮询）。
2. **或采用 WebSocket**：替代 SSE，减少连接数（尤其 Dashboard 页面需要多路数据时）。
3. **连接心跳**：SSE 增加 30 秒一次的心跳 ping，及时检测连接断开。

---

### 5.2 缺乏 API 限流与熔断

**现状**：
- 文档未提及 Rate Limiting 或 Circuit Breaker。
- Agent 自动化操作可能因逻辑错误导致 API 风暴（如无限循环创建 Issue）。

**改进方向**：
1. **按角色限流**：对 MCP 工具和 REST API 增加限流（如 agent 每分钟最多 100 次创建操作）。
2. **内容去重**：对 `create_issue`、`notify_role` 等高频操作增加防抖窗口（如 10 秒内相同内容去重）。
3. **Circuit Breaker**：当后端 API 连续失败 5 次时，MCP 自动进入熔断状态，暂停调用并通知管理员。

---

## 六、监控与可观测性（P2）

### 6.1 监控维度缺失

**现状**（文档 9.1）：
- 现有 Prometheus 指标集中在业务计数，缺少：
  - **数据库性能**：SQLite 慢查询、WAL 文件大小、锁等待时间。
  - **MCP 层**：各工具调用延迟、错误率、按角色分区的 QPS。
  - **工作流**：步骤执行时间、条件分支命中率、并行执行竞争情况。

**改进方向**：
1. **新增指标**：
   - `pm_workflow_step_duration_seconds` — 工作流步骤执行耗时
   - `pm_mcp_tool_duration_seconds` — MCP 工具调用延迟
   - `pm_sqlite_wal_size_bytes` — WAL 文件大小
   - `pm_sqlite_lock_wait_seconds` — 锁等待时间
   - `pm_agent_qps_by_role` — 按角色分区的 QPS
2. **结构化日志**：引入 JSON Format 日志，接入 Loki / ELK，方便按 `agent_id`、`issue_id` 追踪全链路。
3. **分布式追踪**：引入 OpenTelemetry，追踪从 MCP 调用 → API 处理 → 数据库操作的完整链路。

---

## 七、部署与运维问题（P2 / P3）

### 7.1 单点部署无高可用

**现状**（文档 7.1）：
- 所有服务在一台 Docker Host，SQLite 单文件。
- 无主备、无滚动更新策略。

**改进方向**：
1. **高可用部署**：提供 Docker Swarm / Kubernetes Helm Chart 部署方案，支持 backend 多副本（需先解决数据库从 SQLite 到 PG 的迁移）。
2. **健康检查与自动重启**：`pm-mcp` 和 `pm-backend` 增加 Liveness/Readiness Probe。
3. **数据备份**：数据卷增加每日自动备份（如 restic 备份到对象存储或另一台 NAS）。
4. **蓝绿部署**：支持零停机更新，新版本验证通过后再切换流量。

## 八、改进优先级矩阵

| 优先级 | 领域 | 关键动作 | 预期影响 |
|--------|------|----------|----------|
| **P0** | 安全 | MCP 启用 HTTPS / mTLS；前端 Token 改为 httpOnly Cookie；密码管理从环境变量迁移到 Secret 文件 | 防止凭证泄露、XSS 攻击 |
| **P0** | 可靠性 | 工作流状态实时持久化；消息队列改为"写入即落盘"或引入 Redis | 防止重启丢数据、任务中断 |
| **P1** | 数据库 | 提供 PostgreSQL 适配；增加 SQLite 自动备份和 WAL 大小限制 | 支撑长期数据增长 |
| **P1** | MCP | 按角色分端口 / 路径；增加限流和审计日志 | 提升多 Agent 并发稳定性 |
| **P1** | 工作流 | 步骤级超时配置；断点续传；幂等性设计 | 提升工作流健壮性 |
| **P2** | 前端 | SSE 重连降级替代轮询；API 增加防抖 | 降低服务端负载 |
| **P2** | 监控 | 增加数据库 / MCP / 工作流细粒度指标；引入结构化日志 | 提升故障排查效率 |
| **P3** | 部署 | K8s Helm Chart；多节点部署方案 | 支持高可用扩展 |

## 九、总结

当前架构适合 **1–3 个 Agent、家庭内网、低并发** 的 MVP 场景，设计简洁、部署方便。

如果要支撑 **5 个以上 Agent、跨网络协作、7×24 小时运行**，需要在以下三个核心环节先做硬性加固：

1. **安全传输层**：从 HTTP + 明文密码 → HTTPS / mTLS + 短期 Token
2. **数据库持久化**：从 SQLite 单文件 → 可选 PostgreSQL + 自动备份
3. **工作流状态机**：从内存状态 → 实时数据库持久化 + 断点续传

否则，随着版本迭代（1.3.0 之后功能越来越多），技术债务会指数级放大，最终可能导致数据丢失、Agent 协作中断、安全事件等严重后果。
