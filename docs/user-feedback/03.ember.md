## 2. 工具探索体验

### 2.1 项目探索

**调用**：`list_projects`

**返回**：
```
Total: 2 projects
  #2 [active] Test Project (slug=test-project) (0 issues, 0 plans, 0 milestones, 0 servers)
  #1 [active] Default Project (slug=default) (5 issues, 3 plans, 2 milestones, 0 servers)
```

**体验感受**：
- **好的**：统计数据（issues/plans/milestones/servers 计数）一览即知项目活跃度，slug 信息方便引用
- **不足**：
  - 没有项目创建时间/最近活动时间——我无法判断一个项目是刚建的还是长期维护的
  - 没有"我（hermes-agent）在这个项目中的角色/权限"信息
  - 没有 `project_id` 字段——虽然 `#1` 暗示了 ID，但格式上不够明确，后续工具需要 `project_id=1` 时我得自行推断
  - 只有两个状态（active？），没有看到 archived/completed 等状态选项

### 2.2 Issue 完整生命周期

**调用链**：`create_issue` → `list_issues` → `update_issue_status` → `update_issue_priority` → `add_issue_comment`

#### create_issue

**参数填写**：title（必填）、description、priority（P0-P3）、issue_type（task/bug/feature）、project_id、labels。必填项只有一个（title），其余都有默认值，填起来比较顺手。

**返回**：
```
Issue #6 created: [P2] 探索性测试 v2 - Agent 体验报告生成 (status=open) (project_id=1)
```

**感受**：
- 创建后返回了 ID、标题、优先级、状态和项目 ID——核心信息够用
- **但缺少**：创建时间、完整的 Issue 对象（比如我填的 description 哪去了？labels 我没填，有没有默认值？）。如果我想确认 description 是否被正确保存，必须再调 `list_issues` 然后祈祷它返回 description——然而 `list_issues` 也不返回 description！
- `source` 自动标记为 `ai_agent`，这是合理的，但没有区分具体是哪个 Agent（hermes-agent？cline？trae？）

#### list_issues

**筛选测试**：
- `project_id=1` + `status=open`：返回 3 条 ✓
- `project_id=1` + `deferred_only=true`：返回 4 条 ✓
- `project_id=1` + `priority=P1`：返回 5 条 ✓
- `source=ai_agent`（不带 project_id）：返回 6 条（跨项目）✓

**感受**：
- 筛选维度丰富，组合灵活
- **关键缺失**：
  - 不返回 `description`——我只能看到标题，无法在列表层面判断 Issue 的具体内容
  - 不返回 `created_at`/`updated_at`——无法按时间排序或判断时效性
  - 不返回评论数量——不知道一个 Issue 是否有过讨论
  - 不返回 `deferred_to_milestone` 信息——`deferred_only=true` 能筛出 deferred 的，但我看不到它被 defer 到了哪个 milestone
  - 没有 `assignee` 字段——不知道这个 Issue 是谁在负责

#### update_issue_status

**返回**：`Issue #6 status updated to in_progress`

**感受**：
- 简洁明确，但只返回了确认信息，没有返回更新后的完整 Issue 对象
- 状态枚举值（open/in_progress/review/deferred/closed/cancelled）需要外部文档才知道，工具描述里应该列出
- 没有状态转换约束——我可以直接从 open 跳到 closed，也可以从 deferred 跳回 open。这是自由还是隐患？

#### update_issue_priority

**返回**：`Issue #6 priority updated to P1`

**感受**：与 update_issue_status 一样——简洁但信息量少。

#### add_issue_comment

**返回**：`Comment added to Issue #6`

**感受**：
- author 自动使用 Agent 身份，这很好
- 但我看不到评论的 ID、时间戳，也无法查看已有的评论列表
- **关键缺失**：没有 `list_comments` 工具——我发了评论后，无法回溯查看 Issue 上的讨论历史

### 2.3 Plan 审批流程（核心体验）

#### propose_plan

**调用**：`propose_plan(title="v2 探索性测试体验报告生成计划", description="...", project_id=1)`

**返回**：
```
Plan #5 proposed: v2 探索性测试体验报告生成计划 (status=pending_approval, waiting for approval)
```

**感受**：
- 能表达标题和描述，基本够用
- 但 Plan 的结构是扁平的——没有 plan_items 的预定义能力，我无法在提议时就列出"这个计划包含哪些步骤"
- 返回信息足够确认提交成功，但同样缺少创建时间

#### list_plans

**调用**：`list_plans(project_id=1, status=pending_approval)`

**返回**：
```
Total: 4 plans
  #5 [pending_approval] v2 探索性测试体验报告生成计划 (proposed_by=ai_agent)
  ...
```

**感受——这是本次测试的最大痛点**：
- **不返回 description**——我提 Plan 时精心写的描述，列表里完全看不到
- **不返回 reject_reason**——如果 Plan 被拒绝了，我根本不知道为什么。这是审批流程的核心信息
- **不返回 plan_items**——我不知道 Plan 的执行进度
- **不返回审批人/审批时间**——谁批的？什么时候批的？
- 没有单独的 `get_plan` 工具——无法查看单个 Plan 的完整信息

**审批等待体验**：我能做的只有反复调 `list_plans` 检查状态是否变化，然后调 `check_notifications` 看有没有通知。这是一种**无助的轮询**——我不知道人类看了没有、有没有意见、大概什么时候会审批。

#### update_plan_progress

**调用**：`update_plan_progress(plan_id=5, item_title="各工具调用体验评估", status=done)`

**返回**：`PlanItem '各工具调用体验评估' created with status done`

**感受**：
- 能用，但有一个**严重的设计问题**：Plan 还在 `pending_approval` 状态时，我就能往里加 plan_items 并标记完成！这不符合逻辑——Plan 应该先被审批，然后才能开始执行和更新进度
- `item_title` 是自由文本，不是预定义的 ID——如果我想更新一个已有的 plan_item，必须精确匹配 title，这容易出错
- 没有返回 plan_item 的 ID，无法后续引用

#### check_notifications

**返回**：`No notifications.`

**感受**：
- 通知是**纯轮询模式**——我必须主动来问，系统不会推给我
- 没有通知类型分类——即使有通知，我也不知道它是"Plan 审批结果"还是"有人评论了我的 Issue"
- 没有通知的优先级/紧急程度——P0 Issue 被创建了，通知和普通通知没有区分
- 缺少"有新通知"的信号机制——我只能盲目轮询

## 3. 体验痛点汇总

### 3.1 信息层面

**信息太少（需要二次查询）**：
- `list_issues` 不返回 description、created_at、updated_at、评论数、assignee
- `list_plans` 不返回 description、reject_reason、plan_items、审批人、审批时间
- `create_issue` 返回后无法确认 description 是否保存成功
- 没有 `get_issue` / `get_plan` 单条查询工具——无法获取完整对象
- 没有 `list_comments` 工具——无法回溯 Issue 讨论历史

**信息格式不统一**：
- `list_milestones` 返回描述和截止日期，但 `list_issues` 不返回描述
- `list_projects` 用 `#1` 表示 ID，但工具参数需要 `project_id=1`——格式暗示不等于显式字段
- 错误信息不统一：有的返回人类可读文本，有的返回原始 HTTP JSON（如 404、422）

**信息缺失（系统层面）**：
- 没有 `reject_reason` 暴露给 Agent——这是审批闭环的关键信息
- `source=ai_agent` 不区分具体 Agent 身份
- 里程碑统计和实际 deferred Issue 不一致（可能有缓存 bug）

### 3.2 流程层面

**"创建并确认"需要 2 次调用**：
- 创建 Issue 后必须再调 `list_issues` 才能确认，因为 create 返回的信息不够完整
- 理想情况：create 操作返回完整的对象，一次调用即可

**强制依赖链**：
- `defer_issue` 依赖 `list_milestones` 的 milestone_id——必须先查 milestones
- `create_workflow` 的 steps 参数需要手动构造 JSON 字符串
- `update_plan_progress` 需要 plan_id，但 `propose_plan` 只返回 ID 不返回完整对象

**不合理的行为**：
- `update_plan_progress` 在 Plan 仍为 `pending_approval` 时也能操作——应该有状态约束
- Plan 被 reject 后，Agent 不知道原因，可能重复提交相同的 Plan

**审批等待体验**：
- 纯轮询模式，没有推送
- 不知道人类是否已查看、何时可能审批
- 没有超时机制——Plan 可能永远停留在 pending_approval

### 3.3 Agent 自主权层面

**被限制的时刻**：
- 想查看 Issue 的完整信息（description + comments）——没有工具支持
- 想取消 defer——没有 `undefer_issue` 工具
- 想修改已提交的 Plan——没有 `update_plan` 工具
- 想查看工作流执行记录——`list_workflow_runs` 有 bug 不可用
- 想知道其他 Agent 在做什么——完全没有多 Agent 可见性

**困惑的时刻**：
- Issue #6 defer 后 milestone 统计仍为 0——不知道是 bug 还是缓存延迟
- `list_workflow_runs` 报 422——不知道是我的参数问题还是系统 bug
- Plan 处于 pending_approval 时就能更新进度——不确定这是 feature 还是 bug

**多 Agent 冲突风险**：
- `source=ai_agent` 是统称，不区分 hermes-agent/cline/trae
- 两个 Agent 可能同时 `update_issue_status` 导致状态跳变
- 没有"锁"或"认领"机制防止并行操作冲突
- 没有 Agent 活动日志——无法知道其他 Agent 近期做了什么

### 3.4 与人类协作层面

**Plan 审批**：
- 人类能在 Web UI 看到我提的 Plan（推测），但我看不到人类的审批结果细节
- reject 后没有原因反馈，无法形成闭环
- 没有"提醒人类审批"的机制

**评论**：
- `add_issue_comment` 能发评论，但不知道人类是否看到了
- 没有 `list_comments`——我不知道人类是否回复了我的评论

**通知机制**：
- `check_notifications` 是纯轮询——必须主动询问
- 通知为空时没有任何"自上次检查后的变更摘要"
- 没有"紧急通知"的概念——P0 Issue 创建和普通状态变更的通知优先级相同
- 对于长时间运行的 Agent，轮询间隔设多少？太频繁浪费 token，太稀疏错过关键事件

## 4. v2 设计思路

### 4.1 Agent 状态感知增强

**问题**：Agent 进入系统后需要 6-7 次工具调用才能拼出全局状态，且每次新会话都要重来。

**设计方案：新增 `get_context` 工具**

```
get_context(project_id?: int) → {
  project: { id, name, slug, active_since },
  summary: {
    open_issues: { total, by_priority: { P0: n, P1: n, ... } },
    pending_plans: { total, oldest_pending_hours },
    upcoming_milestones: [{ id, title, due_date, days_remaining }],
    recent_activity: [{ type, description, timestamp, agent? }],  // 最近 10 条
    urgent_alerts: [{ type, message }]  // P0 issues, overdue milestones, etc.
  },
  my_state: {
    my_open_issues: n,
    my_pending_plans: n,
    my_unread_notifications: n
  }
}
```

**核心价值**：
- 一次调用获得全局态势感知，替代 6-7 次 list 调用
- `urgent_alerts` 让 Agent 立刻知道需要关注什么
- `my_state` 区分"系统全局状态"和"与我相关的状态"
- `recent_activity` 提供"发生了什么变化"的时间线视角

### 4.2 主动推送 vs 被动轮询

**问题**：当前 Agent 只能轮询 `check_notifications`，无法及时获知审批结果、Issue 变更等关键事件。

**设计方案：三层推送策略**

**第一层（立即可做）：结构化轮询优化**
```
check_notifications(since?: timestamp, types?: [plan_approved, plan_rejected,
  issue_assigned, issue_status_changed, comment_added, ...]) → {
  notifications: [...],
  has_more: bool,
  suggested_poll_interval_seconds: int  // 服务端根据活跃度动态建议
}
```
- 增加 `since` 参数：只获取自上次检查后的新通知
- 增加 `types` 过滤：Agent 可以只关注特定类型
- 服务端动态建议轮询间隔：系统活跃时 30s，安静时 5min

**第二层（中期目标）：Webhook 回调**
```
register_callback(url: string, events: [string], secret: string) → { callback_id }
```
- Agent 启动时注册一个 HTTP 回调端点
- 系统在关键事件发生时 POST 到该端点
- 适用于 Agent 有自己的 HTTP server 的场景

**第三层（远期目标）：MCP 协议扩展**
- 推动 MCP 协议支持 Server-Sent Events 或 WebSocket
- 在 MCP 层面实现"订阅-推送"模式
- 这需要协议层面的标准化，不是单个系统能解决的

### 4.3 Plan 审批的对话式改进

**问题**：Plan reject 后 Agent 不知道原因，可能重复提交；Plan 提议后无法修改，只能重新创建。

**设计方案：对话式审批闭环**

**工具层改进**：

1. **`list_plans` 增加 `reject_reason` 字段**（最小改动，最大价值）
```
list_plans → {
  plans: [{
    id, title, description, status,
    proposed_by, proposed_at,
    approved_by?, approved_at?,
    rejected_by?, rejected_at?,
    reject_reason?,          // ← 新增
    modification_suggestion? // ← 新增：人类建议的修改方向
  }]
}
```

2. **新增 `update_plan` 工具**
```
update_plan(plan_id: int, title?: str, description?: str,
            add_items?: [str], remove_items?: [int]) → Plan
```
- 允许 Agent 根据人类的 reject_reason 调整 Plan 后重新提交
- 状态从 `rejected` → `pending_approval`（修改后自动回到待审批）

3. **审批对话流**
```
Agent propose_plan → Plan(status=pending_approval)
    ↓
Human reject(reason="scope 太大，建议拆分为两个 Plan",
             suggestion="先做 Issue 管理部分，Plan 管理部分后续")
    ↓
Agent 收到通知(type=plan_rejected, reason=..., suggestion=...)
    ↓
Agent update_plan(plan_id, 修改 title 和 description) → Plan(status=pending_approval)
    ↓
Human approve → Agent 收到通知，开始执行
```

4. **`update_plan_progress` 增加状态约束**
- 只有 `approved` 状态的 Plan 才能更新进度
- 对 `pending_approval` 的 Plan 调用应返回错误："Plan 尚未审批，无法更新进度"

### 4.4 Agent 记忆与上下文保持

**问题**：每次 MCP 调用是无状态的，Agent 不记得之前做了什么，也不知道系统的历史变化。

**设计思路：区分三层记忆**

**第一层：系统侧工作记忆（应由系统负责）**
```
AgentSession {
  agent_id: string,          // "hermes-agent"
  session_id: string,
  started_at: timestamp,
  recent_operations: [{      // 最近 50 次操作
    tool, args_hash, result_summary, timestamp
  }],
  current_focus: {           // Agent 当前关注点
    project_id?,
    issue_ids: [],
    plan_ids: []
  }
}
```
- 系统记录每个 Agent 的操作轨迹，下次连接时可恢复上下文
- `current_focus` 让系统知道"这个 Agent 正在忙什么"
- 这不是 Agent 自身的记忆（LLM context），而是系统提供的"你上次做到哪了"

**第二层：跨会话持久状态（应由系统负责）**
```
AgentProfile {
  agent_id: string,
  display_name: string,
```

### 4.5 多 Agent 协调机制

**问题**：多个 Agent（hermes-agent、cline、trae）可能同时操作系统，互相不知道对方在做什么，存在冲突风险。

**设计方案：认领 + 广播 + 冲突检测**

**1. Issue 认领机制**

```
claim_issue(issue_id: int) → { issue, claimed_at }
unclaim_issue(issue_id: int) → { issue }
```
- Agent 对 Issue claim 后，其他 Agent 能看到 `claimed_by: "hermes-agent"`
- Issue 的 `source` 字段从 `ai_agent` 细化为具体 Agent 名：`hermes-agent` / `cline` / `trae`
- 同一 Issue 同时只能被一个 Agent claim，claim 冲突时返回 409 Conflict

**2. Agent 活动广播**

```
get_agent_activity(project_id?: int) → [{
  agent_id: string,
  status: "active" | "idle",
  current_focus: string,      // "正在处理 Issue #6"
  last_action: { tool, target, timestamp },
  claimed_issues: [int]
}]
```
- 每个 Agent 能看到其他 Agent 的实时状态
- 类似于代码编辑器的"谁在线、光标在哪里"的感知

**3. 操作冲突检测**

- `update_issue_status` / `update_issue_priority` 增加乐观锁：`expected_current_status` 参数
- 如果当前状态与预期不符，返回 409 + 当前实际状态，Agent 可据此决策
- 评论操作天然无冲突，不需要锁

**4. 协作约定**

- P0 Issue：创建后自动通知所有 Agent，第一个 claim 的 Agent 负责
- Plan 提议：如果已有 Plan 处理同一主题，后提议的 Agent 收到"已有相关 Plan #N"的提示
- 里程碑：Agent 不应直接修改里程碑定义，需要人类审批

### 4.6 优先改进项（只选一个）

**选择：`list_plans` 暴露 `reject_reason` + 新增 `get_plan` 工具**

**理由**：

Plan 审批是 Agent 与人类协作的核心环节。当前的体验断裂在于：
1. Agent 提了 Plan，然后陷入"盲等"——不知道人类是否看了、何时审批
2. 即使 Plan 被 reject 了，Agent 也无法知道原因——这意味着 Agent 可能重复犯同样的错误
3. 没有 `get_plan` 工具，Agent 无法获取 Plan 的完整信息（description、items、审批详情）

这不是一个"锦上添花"的优化，而是**协作闭环的关键缺失**。没有 reject_reason，Agent 和人类之间就没有真正的对话——只有单方面的"提交→被拒→再提交→再被拒"的死循环。
