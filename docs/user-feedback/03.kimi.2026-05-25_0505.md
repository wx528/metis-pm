### 2.3 Plan 审批流程（核心体验）

#### 2.3.1 提议 Plan
**调用**: `propose_plan`
```json
{
  "title": "Agent体验测试Plan-2026-05-25-0505",
  "description": "这是一个由hermes-agent发起的Plan审批流程测试..."
}
```
**返回**:
```
Plan #9 proposed: Agent体验测试Plan-2026-05-25-0505 (status=pending_approval, waiting for approval)
  描述: ...
  created_at=2026-05-24T21:06:00.323648
```

**体验**:
- ✅ **参数极简**: 只需要 title + description，门槛低
- ✅ **状态自动设置**: 自动为 pending_approval，不需要手动指定
- ⚠️ **无法指定项目**: 没有 project_id 参数
- ⚠️ **无法指定 plan items**: 只能提一个空壳 Plan，具体任务项需要后续通过 `update_plan_progress` 添加
- ❌ **scope 表达受限**: 只有 description 一个自由文本字段，没有 structured 的目标/范围/验收标准字段

#### 2.3.2 查询 Plan 状态
**调用**: `list_plans`
**返回**: 9 个 Plans，包含状态、创建者、描述、进度

**体验**:
- ✅ **状态一目了然**: pending_approval/active/abandoned 三种状态清晰
- ✅ **进度可视化**: 显示 "0/0 items done" 或 "X/Y items done"
- ❌ **关键信息缺失**: **不返回 reject_reason**！这是本次测试的重大发现
  - Plan #4 和 #3 是 abandoned 状态，但 list_plans 只显示 "abandoned"，不显示为什么被拒
  - 作为 Agent，我不知道是人类拒绝了、还是系统自动放弃了、还是其他原因
- ❌ **不返回审批历史**: 不知道谁审批的、什么时候审批的
- ❌ **不返回 plan items 详情**: 只能看到 "0/0 items done"，看不到具体有哪些 items

#### 2.3.3 通知检查
**调用**: `check_notifications`
**返回**:
```
Total: 2 notifications
  ● [info] Plan #9 已提交，等待审批
  ● [info] Issue #8 已创建
```

**体验**:
- ✅ **通知内容清晰**: 包含类型、关联对象、标题
- ⚠️ **需要轮询**: 没有推送机制，Agent 必须主动调用 check_notifications
- ⚠️ **通知不持久**: 没有看到通知的过期/已读机制（mark_notification_read 返回 403，说明有权限控制）
- ❌ **没有审批结果通知**: 我提了 Plan #9 后，通知告诉我 "已提交"，但如果人类审批了/拒绝了，我会收到通知吗？目前无法验证，因为需要人类操作

## 3. 体验痛点汇总

### 3.1 信息层面

#### 信息太多
- `list_plans` 返回所有 Plan 的完整描述，当 Plan 多的时候描述文本很长，但关键信息（如 reject_reason）反而没有
- `get_context` 返回的信息非常全面，但格式是文本块，不是结构化数据，Agent 解析困难

#### 信息太少
- **`list_plans` 不返回 reject_reason**: 这是最大痛点。Plan #4 和 #3 是 abandoned，但我不知道原因
- **`list_plans` 不返回 plan items**: 只能看到 "0/0 items done"，不知道具体有哪些任务
- **`create_issue` 返回不完整**: 创建后没有返回完整对象，需要再调一次 list_issues 确认
- **`list_workflow_runs` 缺少错误详情**: 失败时不知道原因
- **没有 `get_issue` 单条查询**: 只有 list_issues，查单条也要用列表接口

#### 信息格式不统一
- `list_issues` 返回文本块，但 `check_connection` 返回 JSON
- `structuredContent` 字段有时存在有时不存在，内容格式不一致
- 时间戳格式统一为 ISO8601，这是好的

### 3.2 流程层面

#### 工具调用次数
- **"创建 Issue 并确认"**: 需要 2 次调用（create_issue + list_issues）
- **"创建 Plan 并等待审批"**: 需要反复轮询 list_plans，次数不确定
- **"了解项目全局状态"**: 需要调 5+ 个工具（list_issues, list_plans, list_milestones...），或依赖 get_context

#### 强制依赖
- `update_plan_progress` 要求 Plan 必须是 approved 状态，但 Agent 无法自行审批，必须等待人类
- `defer_issue` 需要先创建 milestone，这是合理的依赖
- `trigger_workflow` 需要先创建工作流，合理

#### 审批等待体验
- ❌ **无力感强烈**: 提了 Plan #9 后，我只能 "等待"，不知道人类什么时候会看
- ❌ **只能轮询**: 没有推送机制，只能反复调 list_plans 或 check_notifications
- ❌ **不知道审批结果**: 即使 Plan 被 reject 了，list_plans 也不告诉我原因

### 3.3 Agent 自主权层面

#### 被限制的时刻
- ❌ **无法审批自己的 Plan**: 合理，但限制了自主性
- ❌ **无法查看其他 Agent 的通知**: mark_notification_read 返回 403 "Not your notification"，说明通知是按 Agent 隔离的
- ❌ **无法指定 project_id**: create_issue 和 propose_plan 都没有 project_id 参数，只能操作默认项目
- ❌ **无法删除或修改已创建的 Issue**: 没有 delete_issue 或 update_issue_title 工具

#### 困惑的时刻
- **"我的 Plan 被审批了吗？"**: 不知道，只能轮询
- **"那个 abandoned 的 Plan 为什么被拒？"**: 不知道，list_plans 不显示
- **"workflow 执行成功了吗？"**: Run #3 显示 completed，但自动创建的 Issue #9 没有明确关联

#### 多 Agent 协调
- **不知道其他 Agent 在做什么**: trae 创建了 Issue #7 和 Plan #7，但我没有工具查看 "其他 Agent 的近期活动"
- **可能冲突**: 我和 trae 都在创建 Issue，标题可能重复（如 "Agent体验测试Issue-2026-05-25"）
- **source 字段太粗**: 所有 Agent 都是 `ai_agent`，无法区分 hermes-agent、trae、cline

### 3.4 与人类协作层面

#### 协作顺畅度
- ✅ **Plan 描述清晰**: 人类可以通过 Web UI 看到 Plan 的 title 和 description
- ❌ **Agent 不知道人类是否在线**: 没有 "人类活跃度" 指标
- ❌ **通知是单向的**: Agent 能收到系统通知，但无法确认人类是否看到

#### 审批结果理解
- ❌ **reject 后无法改进**: 不知道原因，只能盲目重提
- ❌ **没有对话线程**: 人类 reject 时不能附言 "请补充技术方案"，Agent 也不能回复 "已补充"

#### 通知机制
- `check_notifications` 是 **主动轮询**，不是推送
- 通知内容清晰，但需要 Agent 记得去查
- 没有 "订阅" 机制，不能指定 "当我的 Plan 被审批时通知我"

## 4. v2 设计思路

### 4.1 Agent 状态感知增强

**当前问题**: Agent 不知道系统全局状态，只能一个个工具查，或者依赖 `get_context` 返回的文本块。

**设计方案**:

1. **增强 `get_context` 工具**
   - 当前 `get_context` 已经存在且非常好用！返回了全局概览、紧急告警、待审批计划、最近活动、我的状态
   - **改进**: 将返回格式从文本块改为结构化 JSON，方便 Agent 解析
   - **新增字段**:
     - `other_agents_activity`: 其他 Agent 最近的操作
     - `my_pending_actions`: 我需要处理的事项（如被 assign 的 Issue、需要跟进的 Plan）
     - `project_health_score`: 项目健康度评分（P0 Issue 数、逾期 milestone 数等）

2. **新增 `subscribe_context_updates` 工具**
   - Agent 可以订阅特定事件（如 "我的 Plan 被审批"、"新的 P0 Issue"）
   - 订阅后，当事件发生时，系统自动调用 Agent 的回调（见 4.2）

3. **项目级上下文缓存**
   - 系统维护每个项目的 "上下文快照"，包含聚合统计
   - Agent 调用 `get_context` 时返回缓存 + 增量更新，减少数据库查询

---

### 4.2 主动推送 vs 被动轮询

**当前问题**: Agent 需要轮询 `check_notifications`，效率低、延迟高、无力感强。

**设计方案**:

1. **MCP 协议扩展：Server-Sent Events (SSE)**
   - 在 HTTP 模式下，MCP Server 可以维护一个 SSE 连接，向 Agent 推送事件
   - 事件类型:
     - `plan_approved` / `plan_rejected` (带 reject_reason)
     - `issue_assigned` / `issue_status_changed`
     - `new_notification`
     - `workflow_run_completed`
   - **优势**: 实时、低延迟、Agent 无需轮询
   - **挑战**: MCP 协议目前是请求-响应模式，SSE 需要协议层面扩展或自定义 transport

2. **Webhook 机制**
   - Agent 注册一个 webhook URL（或 MCP Client 提供的回调端点）
   - 当事件发生时，Server POST 到该 URL
   - **优势**: 与现有 HTTP 基础设施兼容
   - **挑战**: Agent 需要能接收 HTTP 请求，当前 MCP Client 可能不支持

3. **折中方案：长轮询 (Long Polling)**
   - 新增 `wait_for_notification` 工具，阻塞直到有新通知或超时
   - Agent 可以调用 `wait_for_notification(timeout=300)` 代替轮询
   - **优势**: 无需协议扩展，兼容现有 MCP 实现
   - **劣势**: 每个 Agent 需要一个长连接，资源消耗较高

**推荐**: 先实现长轮询作为过渡，同时推动 MCP 协议支持 SSE 或 Webhook。

---

### 4.3 Plan 审批的对话式改进

**当前问题**: reject 后 Agent 不知道原因（list_plans 不返回 reject_reason），可能重复提交相同内容。

**设计方案**:

1. **暴露 reject_reason 到 MCP 层**
   - 后端 API 已支持 reject_reason 字段，MCP 工具层需要暴露
   - `list_plans` 和 `get_plan` 返回 reject_reason（如果有）

2. **新增 `revise_plan` 工具**
   - 当前已存在！Agent 可以调用 `revise_plan(plan_id, title, description)` 修改被拒绝的 Plan
   - **改进**: revise_plan 时，系统自动关联原 Plan 的 reject_reason，提示 Agent "上次被拒原因是：..."

3. **对话式审批线程**
   - 每个 Plan 有一个 "审批对话线程"，类似 Issue 的评论
   - 人类 reject 时可以评论："请补充性能测试方案"
   - Agent 回复："已补充，详见更新后的 description"
   - 人类再次审批
   - **实现**:
     - 新增 `add_plan_comment` 工具
     - `list_plan_comments` 查看审批对话历史
     - Plan 详情页显示完整对话线程

4. **审批建议模板**
   - 人类 reject 时，系统提供快速选项：
     - "范围太大，请拆分"
     - "缺少技术方案"
     - "时间不可行"
     - "与现有 Plan 重复"
   - 选择后自动生成结构化的 reject_reason，Agent 更容易理解

### 4.4 Agent 记忆与上下文保持

**当前问题**: 每次 MCP 调用都是独立的，Agent 不记得之前做了什么。

**设计方案**:

1. **系统级 Agent 工作记忆**
   - 新增 `get_agent_memory` / `set_agent_memory` 工具（已存在！）
   - 系统为每个 Agent 维护一个 key-value 存储
   - Agent 可以保存：
     - `last_action`: 最近操作的时间戳和摘要
     - `pending_plans`: 我提交但未审批的 Plan ID 列表
     - `context_notes`: 对项目的理解笔记
   - **优势**: 跨会话保持，Agent 重启后仍能恢复上下文

2. **会话级上下文**
   - MCP Server 维护每个 Agent 的 "会话状态"
   - 包含：最近操作的缓存、当前 focus 的 Issue/Plan、未完成的 workflow
   - Agent 调用 `get_context` 时，系统注入会话上下文

3. **区分 "系统记忆" 和 "Agent 记忆"**
   | 类型 | 内容 | 由谁维护 |
   |------|------|----------|
   | 系统记忆 | 项目状态、Issue 历史、Plan 审批记录 | 系统 |
   | Agent 记忆 | Agent 的偏好、笔记、待办 | Agent 自己 |
   | 协作记忆 | 人类与 Agent 的对话历史 | 系统 |

4. **自动上下文注入**
   - Agent 每次调用工具时，系统自动在 prompt 中注入相关上下文
   - 例如：调用 `update_issue_status` 时，系统自动提供该 Issue 的当前状态和历史

### 4.5 多 Agent 协调机制

**当前问题**: 多个 Agent（trae、hermes-agent、cline）可能重复工作、互相不知道对方在做什么。

**设计方案**:

1. **细化 source 字段**
   - 当前所有 Agent 都是 `ai_agent`
   - **改为**: `hermes-agent`、`trae`、`cline`、`user`
   - 在 list_issues / list_plans 中显示具体 Agent 名称

2. **Agent 活动广播**
   - 新增 `list_agent_activities` 工具，查看所有 Agent 的近期操作
   - 返回：Agent 名称、最近操作时间、最近操作类型、当前 focus
   - 类似 "谁在线" 功能

3. **任务认领机制**
   - Issue 新增 `assignee` 字段，Agent 可以 "认领" Issue
   - `claim_issue(issue_id)` / `unclaim_issue(issue_id)`
   - 其他 Agent 看到 Issue 已被认领，避免重复工作

4. **冲突检测**
   - 当两个 Agent 同时操作同一资源时，系统检测冲突
   - 例如：Agent A 更新 Issue #8 状态时，Agent B 也同时更新
   - 系统返回冲突提示，后操作的 Agent 需要确认

5. **Agent 间通信**
   - 新增 `send_agent_message(to_agent, content)` 工具
   - 例如：hermes-agent 可以发消息给 trae："Issue #6 我正在处理，请不要重复"
   - 接收方通过 `check_notifications` 收到消息

### 4.6 优先改进项（只选一个）

**选择**: **暴露 reject_reason 并支持对话式 Plan 审批**

**理由**:
1. **影响最大**: Plan 审批是 Agent 与人类协作的核心流程，当前 reject 后 Agent 完全不知道原因，导致无法改进、可能重复犯错
2. **实现成本低**: 后端 API 已支持 reject_reason 字段，只需在 MCP 工具层暴露，工作量小
3. **用户体验立竿见影**: Agent 能看懂人类的反馈，形成 "提议 → 被拒 → 了解原因 → 改进 → 再提议" 的闭环
4. **为其他改进奠基**: 对话式审批线程建立后，可以复用到 Issue 讨论、Workflow 调试等场景

**具体设计方案**:

**阶段 1（立即做）**:
- 修改 `list_plans` 工具，在返回 abandoned Plan 时包含 `reject_reason` 字段
- 修改 `propose_plan` 的返回，如果之前有相似标题的 Plan 被 reject，提示 Agent

**阶段 2（短期）**:
- 新增 `get_plan(plan_id)` 工具，返回 Plan 完整信息（含 reject_reason、审批历史）
- 优化 `revise_plan` 工具，在修改界面显示原 reject_reason

**阶段 3（中期）**:
- 新增 `add_plan_comment` 和 `list_plan_comments` 工具
- 在 Plan 详情中建立 "审批对话线程"
- 人类 reject 时，系统引导人类填写 reject_reason（必填或选模板）

**阶段 4（长期）**:
- 结合 4.2 的推送机制，Plan 被 reject 时实时通知 Agent
- Agent 收到通知后自动调用 `get_plan` 查看原因，决定是 revise 还是放弃
