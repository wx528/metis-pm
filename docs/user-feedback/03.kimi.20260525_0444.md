### 2.2 Issue 完整生命周期

#### 2.2.1 创建 Issue
**调用**: `create_issue`
- title: `Agent体验测试Issue-2026-05-25`
- description: 完整描述文本
- priority: `P2`
- issue_type: `task`
- labels: `test,mcp-exploration`
- project_id: `1`

**返回**:
```
Issue #6 created: [P2] Agent体验测试Issue-2026-05-25 (status=open, source=ai_agent) (project_id=1)
  描述: ...
  标签: test,mcp-exploration
  created_at=2026-05-24T20:43:46.010003
```

**体验感受**:
- **参数体验**: 必填项只有 `title`，其他都是可选，区分清楚。`source` 自动标记为 `ai_agent`，`project_id` 需要手动指定。
- **返回信息**: 返回了完整的 Issue 对象（ID、状态、source、描述、标签、时间戳），足够确认创建成功。比只返回 ID 好很多。
- **小困惑**: `source` 自动填了 `ai_agent`，但我在 `get_context` 里看到另一个 Agent `trae` 创建的 Issue 也是 `source=ai_agent`——这意味着**多 Agent 场景下无法从 source 区分具体是谁**。

#### 2.2.2 更新状态
**调用**: `update_issue_status` (issue_id=6, status=`in_progress`)

**返回**: 包含更新后的完整状态信息，包含 updated_at。

**体验感受**: 状态可选值（open/in_progress/review/deferred/closed/cancelled）清晰，返回即时确认成功。但**没有变更历史**——我不知道这个 Issue 之前是什么状态。

#### 2.2.3 更新优先级
**调用**: `update_issue_priority` (issue_id=6, priority=`P1`)

**体验感受**: 和更新状态类似，返回即时。但同样**没有变更历史/审计日志**。

#### 2.2.4 添加评论
**调用**: `add_issue_comment` (issue_id=6, content=`...`)

**返回**: `Comment #2 added to Issue #6 by hermes-agent at 2026-05-24T20:43:53.205906`

**体验感受**: 顺畅。author 自动使用 Agent 身份 `hermes-agent`，不需要我手动填。但返回的 comment ID 是 `#2`，而这是该 Issue 的第一条评论——说明**评论 ID 是全局自增的**，不是 per-issue 的，有点反直觉。

#### 2.2.5 查询评论
**调用**: `list_comments` (issue_id=6)

**返回**: 1 条评论，包含作者、内容、时间戳。

**体验感受**: 信息密度合适。但**没有分页参数**——如果 Issue 有 100 条评论，会一次性全返回。

#### 2.2.6 按条件筛选
**调用**: `list_issues` (project_id=1, priority=`P1`)

**返回**: 2 条 P1 Issue，包含完整的描述、状态、时间戳。

**体验感受**: 筛选条件够用（project_id, priority, status, source, milestone_id, deferred_only, limit）。返回信息密度高，每条都有描述、状态、时间戳。但**缺少排序参数**——不能按 updated_at 排序。

#### 2.2.7 查询 deferred Issue
**调用**: `list_issues` (project_id=1, status=`deferred`)

**返回**: 2 条 deferred Issue，包含"推迟到: milestone #1"和 defer reason。

**体验感受**: 很好，deferred 的 Issue 会显示关联的 milestone 和原因。

### 2.3 Plan 审批流程（重点）

#### 2.3.1 提议 Plan
**调用**: `propose_plan`
- title: `Agent体验测试Plan-2026-05-25`
- description: 详细描述
- project_id: `1`

**返回**:
```
Plan #8 proposed: Agent体验测试Plan-2026-05-25 (status=pending_approval, waiting for approval)
  描述: ...
  project_id=1
  created_at=2026-05-24T20:44:06.506359
```

**体验感受**:
- **参数体验**: 只能填 `title` 和 `description`，没有"计划项列表"、"预期目标"、"时间节点"等字段。Plan 的 scope 表达受限——我只能在 description 里写大段文字，没有结构化方式。
- **返回信息**: 返回了完整 Plan 对象，包含 status=`pending_approval`，足够确认。

#### 2.3.2 查询 Plan 状态
**调用**: `list_plans` (project_id=1)

**返回**: 7 个 Plan，包含 status、by、描述、进度。

**关键发现**:
- `list_plans` **确实返回了 `reject_reason`**！Plan #5 显示：`拒绝原因: Need more implementation details before approval`
- 但 Plan #4 和 #3（也是 abandoned）**没有显示 reject_reason**——说明 reject_reason 是可选填的，不是每次都有。

**体验感受**:
- **正面**: 能看到 reject_reason 是很大的帮助，Agent 知道为什么被拒。
- **负面**: 但**没有"审批人"和"审批时间"**——我不知道是谁拒的、什么时候拒的。
- **负面**: Plan 列表返回的是纯文本摘要，没有结构化的 `items` 列表（进度显示 `0/0 items done`，但我看不到 items 是什么）。

#### 2.3.3 等待审批的体验
**调用**: `check_notifications` (limit=10, unread_only=false)

**返回**: `No notifications.`

**体验感受**:
- **无力感强烈**: 我提了 Plan #8 后，不知道人类审批了没有。`check_notifications` 返回空，说明**通知不是实时生成的**——可能是审批时才会产生通知，或者通知有延迟。
- **只能轮询**: 我的唯一选择是反复调 `list_plans` 查 status，或者调 `check_notifications` 看有没有新消息。这种"不知道对方收到没有"的感觉很像发微信后对方没回，你不知道是没看到还是不想回。

#### 2.3.4 更新 Plan 进度（失败体验）

**返回**: `Error: Plan #8 状态为 'pending_approval'，无法更新进度。只有 approved(active) 或 completed 状态的 Plan 才能更新进度。`

**体验感受**: 错误信息清晰，告诉我为什么失败。但这也意味着——**Agent 提的 Plan 在被批准前，完全无法做任何操作**，只能干等。

## 3. 体验痛点汇总

### 3.1 信息层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **Plan 信息不完整** | `list_plans` 返回进度 `0/0 items done`，但不显示 items 列表 | Agent 不知道 Plan 里具体有什么任务 |
| **缺少变更历史** | Issue 状态/优先级更新后，没有 audit log | Agent 不知道 Issue 经历了什么 |
| **Milestone 统计不准** | defer 了 Issue 到 milestone，但统计仍显示 0 | 信息不可信 |
| **工作流执行详情缺失** | `list_workflow_runs` 不显示步骤输出 | 无法排查工作流问题 |
| **评论 ID 全局自增** | Issue #6 的第一条评论 ID 是 #2 | 反直觉，容易混淆 |
| **通知为空** | 做了大量操作后，`check_notifications` 仍返回空 | 不确定通知机制是否工作 |

### 3.2 流程层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **创建后需手动确认** | 创建 Issue/Plan 后，如果想确认列表里有，需再调一次 list | 多一次无意义调用 |
| **Plan 审批前无法操作** | pending_approval 的 Plan 不能更新进度 | Agent 只能干等 |
| **缺少批量操作** | 不能批量更新 Issue 状态、批量 defer | 效率低 |
| **审批结果只能轮询** | 没有推送机制，只能反复 list_plans | 浪费调用、体验差 |

### 3.3 Agent 自主权层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **不知道全局状态** | 每次交互都是独立的，Agent 不记得之前做了什么 | 重复查询、上下文断裂 |
| **无法区分其他 Agent** | `trae` 创建的 Issue 也是 `source=ai_agent` | 可能重复工作、冲突 |
| **没有工作记忆** | 系统不保存 Agent 的会话状态 | 每次重新开始 |
| **权限边界模糊** | 不知道哪些操作需要审批、哪些可以自主做 | 决策困难 |

### 3.4 与人类协作层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **Plan 表达受限** | 只能填 title + description，没有结构化字段 | 人类可能看不懂 Plan 的 scope |
| **reject 后缺少对话** | 能看到 reject_reason，但无法直接回复/修改 | 需要重新 create，不是迭代 |
| **通知机制不透明** | `check_notifications` 经常为空 | 不确定人类有没有看到我的操作 |
| **没有"@人类"机制** | 评论不能 @ 特定用户 | 协作效率低 |

## 4. v2 设计思路

### 4.1 Agent 状态感知增强

**当前问题**: Agent 不知道系统的全局状态，只能一个个工具查。每次对话开始时，Agent 像"失忆"了一样。

**设计方案**:

1. **新增 `get_context` 工具**（已存在！测试中已验证）
   - 返回全局概览、紧急告警、待审批 Plan、最近活动、我的状态
   - **改进建议**: 在每次 Agent 会话开始时**自动注入** `get_context` 的结果，不需要 Agent 手动调用
   - 增加"与我相关的未读通知数"、"我创建的 Plan 状态变化"

2. **Agent 工作空间缓存**
   - 系统维护每个 Agent 的 `last_seen_context` 时间戳
   - Agent 再次连接时，返回"自你上次离开后发生的变化"（delta 模式）
   - 例如："2 个 Plan 被审批，1 个 Issue 被评论"

3. **项目健康度仪表盘**
   - `get_context` 增加：`issue_burn_down`（本周关闭/新增）、`plan_approval_rate`（审批通过率）、`agent_activity_score`（本 Agent 活跃度）

---

### 4.2 主动推送 vs 被动轮询

**当前问题**: Agent 需要轮询 `check_notifications` 才知道审批结果。MCP 协议是请求-响应模式，没有推送。

**设计方案**:

1. **短轮询优化（即时方案）**
   - `check_notifications` 支持 `since` 参数：`check_notifications(since="2026-05-25T04:00:00")`
   - 只返回该时间之后的通知，减少数据传输
   - 增加 `long_polling` 模式：请求挂起 30 秒，有新通知时立即返回

2. **Webhook 回调（中期方案）**
   - 系统支持配置 Agent 的 webhook URL
   - 当 Plan 被审批/reject、Issue 被分配时，POST 到 Agent 的回调地址
   - Agent 侧需要一个小型 HTTP 服务接收推送

3. **MCP 协议扩展（长期方案）**
   - 向 MCP 社区提案：支持 `server→client` 的 notification 通道
   - 或者使用 SSE (Server-Sent Events) 作为 MCP 的传输层扩展
   - 在 stdio 模式下，Server 可以主动写 JSON-RPC notification 到 stdout

4. **Agent 侧轮询策略（立即可做）**
   - 在 Agent 的 system prompt 中植入"轮询策略"：
     - 提交 Plan 后，每 5 分钟 check 一次
     - 发现状态变化后，主动汇报给用户

---

### 4.3 Plan 审批的对话式改进

**当前问题**: reject 后 Agent 知道原因（`list_plans` 已返回 reject_reason），但**无法直接修改后重新提交**，只能创建新 Plan。没有形成闭环。

**设计方案**:

1. **Plan 版本迭代机制**
   - 新增 `revise_plan(plan_id, new_title, new_description)` 工具
   - revise 后 Plan 状态回到 `pending_approval`，保留历史版本
   - `list_plans` 显示 `version: 3`，可查看历史版本

2. **对话式审批线程**
   - 每个 Plan 有一个"审批线程"（类似评论）
   - 人类 reject 时，可以写：`reject_reason: "缺少成本估算" + suggest: "请补充预算部分"`
   - Agent 收到后，调用 `add_plan_comment(plan_id, "已补充预算：xxx")`
   - 人类看到评论后，可以选择 `approve` 或继续 `reject`

3. **Plan 结构化字段**
   - 除了 title/description，增加：
     - `goals`: 目标列表（可勾选）
     - `timeline`: 时间线（里程碑节点）
     - `risks`: 风险列表
     - `resources`: 所需资源
   - 这样人类审批时，可以针对具体字段提意见："timeline 太乐观"

4. **审批通知增强**
   - Plan 被 reject 时，自动生成通知给创建者
   - 通知内容包含 reject_reason 摘要
   - Agent `check_notifications` 能立即看到

---

### 4.4 Agent 记忆与上下文保持

**当前问题**: 每次 MCP 调用都是独立的，Agent 不记得之前做了什么。系统也没有 Agent 的工作记忆。

**设计方案**:

1. **系统级 Agent 工作记忆（推荐）**
   - 新增 `agent_memory` 表：`agent_id`, `key`, `value`, `updated_at`
   - 提供工具：`set_agent_memory(key, value)`, `get_agent_memory(key)`, `list_agent_memory()`
   - 使用场景：
     - Agent 记录"上次检查的 Plan ID"
     - Agent 记录"当前正在处理的目标"
     - Agent 记录"用户的偏好"
   - **优势**: 记忆持久化，换会话不丢失；多 Agent 隔离

2. **会话级上下文缓存**
   - 系统自动记录当前会话的操作历史
   - 提供 `get_session_history(limit=10)` 工具
   - Agent 可以问"我刚才创建了哪个 Issue？"

3. **Agent 自身记忆（当前做法）**
   - 靠 Agent 的 LLM context window 记住
   - **劣势**: 上下文长了会丢失；换会话完全丢失
   - **建议**: 系统级记忆作为"外存"，LLM context 作为"内存"

4. **操作原子性标记**
   - 支持 `transaction_id` 参数：一组操作标记为同一个事务
   - 如果中途失败，可以 `rollback_transaction(transaction_id)`
   - 例如：创建 Issue + 添加评论 + defer 到 milestone，要么全成功要么全回滚

### 4.5 多 Agent 协调机制

**当前问题**: `trae` 和 `hermes-agent` 都在操作同一个项目，但互相不知道对方在做什么。`source=ai_agent` 无法区分具体 Agent。

**设计方案**:

1. **source 字段细化**
   - `source` 从 `ai_agent` 改为具体 Agent 名：`hermes-agent`, `trae`, `cline`
   - 新增 `agent_id` 字段，精确标识操作者
   - `list_issues` 支持按 `agent_id` 筛选

2. **Agent 活动广播**
   - 新增 `list_agent_activity(limit=10)` 工具
   - 返回最近所有 Agent 的操作："trae 创建了 Issue #5"、"hermes-agent defer 了 Issue #6"
   - 类似 GitHub 的 activity feed

3. **任务认领机制**
   - Issue 增加 `claimed_by` 字段
   - Agent 可以调用 `claim_issue(issue_id)`
   - 其他 Agent 看到 `claimed_by=trae`，就知道这个 Issue 有人在处理了
   - 避免重复工作

4. **冲突检测**
   - 当两个 Agent 同时更新同一个 Issue 时，系统检测并发冲突
   - 返回 `409 Conflict`，包含对方的修改内容
   - Agent 可以选择覆盖、合并或放弃

5. **Agent 间通信**
   - 新增 `send_agent_message(to_agent_id, content)` 工具
   - 例如：hermes-agent 可以给 trae 发消息："Issue #5 我测试过了，没问题"
   - 接收方通过 `check_notifications` 看到

### 4.6 你最想让开发者优先做的一个改进

**选择**: **新增 `get_context` 工具并在每次 Agent 会话开始时自动注入**

**理由**:
1. **影响最大**: 解决 Agent "失忆" 的核心痛点，让 Agent 每次交互都知道"现在发生了什么"
2. **实现成本最低**: 后端已有数据，只需封装一个聚合查询接口
3. **立即可用**: 不需要改 MCP 协议、不需要人类配合、不需要多 Agent 协调
4. **体验提升最明显**: 从"盲人摸象"到"全局在握"

**具体设计方案**:

```yaml
# 工具: get_context
参数:
  project_id: int (可选，不传则返回全局)
返回结构:
  overview:
    issues_total: 6
    issues_p0: 1
    issues_open: 4
    plans_pending_approval: 5
    servers_total: 0
  alerts:
    - type: p0_issue
      message: "1 个 P0 紧急 Issue 需要立即处理"
      issue_id: 1
    - type: pending_plan
      message: "4 个 Plan 等待审批"
      plan_ids: [8, 6, 2, 1]
  pending_plans:
    - id: 8
      title: "Agent体验测试Plan-2026-05-25"
      proposed_by: "hermes-agent"
      created_at: "2026-05-24T20:44:06"
  recent_activity:
    - type: issue_created
      entity_id: 6
      agent: "hermes-agent"
      time: "2026-05-24T20:43:46"
  my_status:
    open_issues: 4
    unread_notifications: 0
    pending_plans: 1
  delta_since_last_visit:  # 新增！
    - "Plan #8 被创建"
    - "Issue #6 被 defer"
```

**自动注入机制**:
- 在 MCP Server 配置中增加 `auto_inject_context: true`
- 每次 Agent 连接时，系统自动调用 `get_context` 并将结果注入到 Agent 的 system prompt 中
- Agent 不需要手动调用，就能知道全局状态
