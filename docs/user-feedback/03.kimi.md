### 1.3 意外发现：`get_context` 工具

在测试过程中，我发现了一个**未在附录清单中列出**的工具：`get_context(project_id)`。这是一个"全局态势感知"工具，一次调用返回：
- 项目概览（Issue/Plan/Server 统计）
- 紧急告警（P0 Issue、待审批 Plan）
- 待审批计划列表
- 最近活动日志
- 我的状态（未读通知数）

这个工具的存在说明系统已经在向"Agent 状态感知"方向探索，但它是"隐藏"的——用户文档中没有提及。这是一个重要的发现。

### 2.1 项目探索

**调用**：`list_projects`

**返回**：
```
Total: 1 projects
  #1 [active] Default Project (slug=default) (3 issues, 5 plans, 0 milestones, 0 servers)
```

**体验感受**：

- **缺失字段**：没有返回项目描述、创建时间、负责人、最近更新时间。如果项目很多，仅凭 slug 和统计数字很难判断哪个是当前活跃的

**改进建议**：返回 `updated_at` 和 `description` 字段，方便 Agent 判断项目新鲜度。

### 2.2 Issue 完整生命周期

#### 2.2.1 创建 Issue

**调用**：`create_issue`
- title: "MCP探索性测试Issue"
- description: "这是一个由hermes-agent发起的MCP Server探索性测试Issue..."
- priority: "P2"
- issue_type: "task"
- project_id: 1

**返回**：
```
Issue #4 created: [P2] MCP探索性测试Issue (status=open, source=ai_agent) (project_id=1)
  描述: ...
  created_at=2026-05-24T19:37:18.485222
```

**体验**：
- **参数友好**：必填项只有 `title`，其余都是可选，且有合理的默认值
- **source 自动标记**：确实自动设置为 `ai_agent`，不需要手动填
- **返回信息够用**：返回了完整的 Issue 对象（ID、标题、状态、source、project_id、描述、创建时间），不是只返回一个裸 ID
- **小困惑**：返回的状态显示 `status=open`，但我没有显式传 status 参数，说明默认值工作正常

#### 2.2.2 更新状态

**调用**：`update_issue_status` (issue_id=4, status="in_progress")

**返回**：
```
Issue #4 status updated to in_progress
  标题: MCP探索性测试Issue | 优先级: P2 | updated_at=...
```

**体验**：
- 状态可选值明确：`open/in_progress/review/deferred/closed/cancelled`
- 返回信息中**优先级还是 P2**，说明 update_status 不会返回更新后的完整对象（或者返回的是更新前的快照）。实际上我后面单独调了 update_priority 才变成 P1，所以这里的 P2 是更新前的状态

#### 2.2.3 更新优先级

**调用**：`update_issue_priority` (issue_id=4, priority="P1")

**返回**：
```
Issue #4 priority updated to P1
  标题: MCP探索性测试Issue | 状态: in_progress | updated_at=...
```

**体验**：
- 优先级可选值明确：P0/P1/P2/P3
- 返回信息中状态显示 `in_progress`，说明这次返回的是更新后的状态
- **不一致**：update_status 返回更新前的优先级，update_priority 返回更新后的状态。这种不一致让我有点困惑

#### 2.2.4 添加评论

**调用**：`add_issue_comment` (issue_id=4, content="Issue已创建成功...")

**返回**：`Comment added to Issue #4`

**体验**：
- **过于简洁**：只返回了成功提示，没有返回评论 ID、创建时间、author 信息
- 我无法确认这条评论是否真的被添加了，除非再调一次 `list_issues` 查看
- author 确实自动使用了 Agent 身份，但我看不到确认

#### 2.2.5 查询 Issue 列表

**调用**：`list_issues` (project_id=1, limit=10)

**返回**：包含 #4 的完整信息，包括 defer 到的 milestone 和 reason

**筛选测试**：
- `priority="P0"`：成功筛选出 1 条
- `status="open"`：成功筛选出 3 条
- `source="ai_agent"`：成功筛选出 4 条

**体验**：
- **筛选条件够用**：支持 project_id、priority、status、source、milestone_id 等多维度筛选
- **信息密度高**：每条 Issue 返回了标题、优先级、状态、source、类型、描述、创建/更新时间、defer 信息
- **列表 vs 详情**：列表返回的信息已经很完整，不需要再调详情接口

#### 2.2.6 Defer Issue

**调用**：`defer_issue` (issue_id=4, milestone_id=1, reason="...")

**返回**：
```
Issue #4 deferred to milestone #1: 将测试Issue暂缓到MCP测试里程碑...

**体验**：
- **操作顺畅**：参数直观（issue_id, milestone_id, reason）
- **reason 能记录暂缓原因**：很好，方便后续追溯
- 返回信息直接确认了操作结果

**调用**：`propose_plan`

#### 2.3.2 查询 Plan 状态

**调用**：`list_plans` (project_id=1, limit=10)

**返回**：
```
Total: 6 plans
  #6 [pending_approval] MCP Server v2改进计划 (proposed_by=ai_agent)
    描述: ...
    进度: 0/0 items done
  #5 [abandoned] Plan with reject reason (proposed_by=user)

**关键发现**：

**体验**：
- 能看到 reject_reason 让我松了一口气——之前担心完全看不到拒绝原因

- **proposed_by 字段很有用**：能区分是 user 还是 ai_agent 提的 Plan

## 3. 体验痛点汇总

### 3.1 信息层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **信息不一致** | `update_issue_status` 返回更新前的优先级，`update_priority` 返回更新后的状态 | Agent 困惑于返回的是"更新前"还是"更新后"的快照 |
| **信息缺失** | `add_issue_comment` 只返回成功提示，不返回评论 ID、时间、author | 无法确认评论是否真的创建成功 |
| **信息隐藏** | `list_workflows` 的 steps 显示为 `?` | Agent 不知道工作流具体做什么 |
| **文档与实现不一致** | 附录说 step_type 支持某些值，实际 enum 不同 | Agent 需要试错才能发现正确的值 |
| **reject_reason 不稳定** | 有的 Plan 显示拒绝原因，有的不显示 | Agent 无法依赖该字段判断被拒原因 |
| **通知为空** | 完成大量操作后 `check_notifications` 仍返回空 | 不确定通知机制是否工作 |

### 3.2 流程层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **创建后确认需二次查询** | 创建 Issue/Plan/Comment 后，返回信息虽完整但 Agent 仍想"确认" | 需要额外调用 list 工具验证 |
| **审批等待无力感** | Plan 提交流 pending_approval 后，Agent 只能轮询 `list_plans` | 不知道人类什么时候会审批 |
| **强制依赖链** | defer Issue 需要先创建 Milestone，更新 plan_progress 需要先等审批 | 流程合理但等待期间 Agent 无事可做 |
| **工作流执行记录无法查看** | `list_workflow_runs` 报错 422 | 无法监控工作流执行历史 |

### 3.3 Agent 自主权层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **不知道全局状态** | 每次交互开始时，Agent 不知道系统当前发生了什么 | 需要逐个工具查询，效率低 |
| **没有"工作记忆"** | 每次 MCP 调用都是独立的，系统不记得 Agent 刚才做了什么 | 重复查询、上下文丢失 |
| **step_type 无 schema** | 创建工作流时不知道合法的 step_type 和 config 格式 | 只能试错 |
| **无法感知其他 Agent** | `source="ai_agent"` 是统一的，不区分 hermes-agent/trae/cline | 不知道其他 Agent 在做什么 |
| **Plan scope 表达受限** | propose_plan 只有 description 文本，无法结构化任务项 | 人类可能看不懂 Plan 的具体内容 |

### 3.4 与人类协作层面

| 痛点 | 描述 | 影响 |
|------|------|------|
| **Plan 审批无对话** | reject 后 Agent 看到原因（如果有），但无法直接"回复"或修改 | 需要重新 propose_plan，形成新的循环 |
| **通知是轮询而非推送** | `check_notifications` 需要 Agent 主动调用 | 可能错过审批结果，或频繁无效轮询 |
| **人类看不到 Agent 的"意图"** | Agent 的操作（如更新状态、defer）只有结果记录，没有意图说明 | 人类不理解 Agent 为什么这样做 |
| **评论体验单向** | Agent 可以评论 Issue，但无法知道人类是否回复了 | 对话不闭环 |

## 4. v2 设计思路

### 4.1 Agent 状态感知增强

**当前问题**：Agent 不知道系统的全局状态，只能一个个工具查。虽然 `get_context` 已经存在，但它是"隐藏"的，且返回的是纯文本摘要，不是结构化数据。

**设计方案**：

1. **正式化 `get_context` 工具**
   - 将其列入官方工具清单，作为 Agent 每次会话开始时的"首选入口"
   - 返回结构化 JSON（而非纯文本），包含：
     ```json
     {
       "project_summary": {
         "issue_counts": {"total": 4, "P0": 1, "P1": 1, "open": 3, "deferred": 1},
         "plan_counts": {"total": 6, "pending_approval": 3, "active": 0},
         "my_open_issues": 3,
         "unread_notifications": 0
       },
       "urgent_alerts": [
         {"type": "P0_issue", "issue_id": 1, "title": "P0??Issue"},
         {"type": "pending_plan", "plan_id": 6, "title": "MCP Server v2改进计划"}
       ],
       "recent_activity": [
         {"type": "issue_created", "id": 4, "by": "hermes-agent", "at": "2026-05-24T19:37:18"}
       ],
       "requires_action": [
         {"type": "plan_approval_waiting", "plan_id": 6, "waiting_since": "..."}
       ]
     }
     ```

2. **增加 `get_context` 的过滤维度**
   - 支持 `since` 参数："自从我上次查询后发生了什么"
   - 支持 `focus` 参数：`issue`/`plan`/`milestone`/`all`，让 Agent 按需获取

3. **在每次写操作后自动返回"影响摘要"**
   - 例如 `update_issue_status` 返回时，附带："此 Issue 现在属于 3 个 open issues 之一，项目还有 1 个 P0 需要关注"

---

### 4.2 主动推送 vs 被动轮询

**当前问题**：Agent 需要轮询 `check_notifications` 才知道审批结果。MCP 协议是请求-响应模式，没有原生推送机制。

**设计方案**：

1. **短轮询优化（立即可做）**
   - `check_notifications` 增加 `since` 参数和 `long_polling` 模式
   - 如果 `long_polling=true`，服务端保持连接 30 秒，有新通知时立即返回，否则超时返回空
   - 减少 Agent 的无效轮询次数

2. **Webhook 回调机制（中期）**
   - 允许 Agent 注册一个 webhook URL（或 MCP Server 向 Agent 的 HTTP 端点推送）
   - 事件类型：`plan_approved`, `plan_rejected`, `issue_assigned`, `mention_in_comment`
   - 需要 Agent 侧有一个轻量级 HTTP 接收端（可以是 Hermes 内部的一个端口）

3. **MCP 协议扩展（长期）**
   - 向 MCP 协议提案：增加 `server→client` 的 notification 通道
   - 类似 JSON-RPC 的 notification，Server 可以在任何时候向 Client 推送事件
   - 这样 `check_notifications` 可以从"轮询"变成"监听"

---

### 4.3 Plan 审批的对话式改进

**当前问题**：reject 后 Agent 知道原因（如果 reject_reason 有值），但无法直接回复或修改，只能重新 propose_plan，形成断裂的循环。

**设计方案**：

1. **暴露 `reject_reason` 为稳定字段**
   - 确保 `list_plans` 和 `get_plan`（如有）始终返回 `reject_reason`（可为 null）
   - 当前 behavior 是不稳定显示，需要统一

2. **增加 `revise_plan` 工具**
   - 不是重新 create，而是基于原 Plan 创建一个新版本
   - 参数：`plan_id`, `new_title`, `new_description`, `revision_note`（说明根据什么反馈修改的）
   - 后端记录 Plan 的版本历史，人类可以看到"这是第 2 版，根据'Need more details'修改"

3. **Plan 结构化表达**
   - `propose_plan` 的 description 支持 Markdown + 结构化任务项：
     ```markdown
     ## 目标
     ...
     ## 任务项
     - [ ] 任务1: 预计2天
     - [ ] 任务2: 预计3天
     ## 风险
     ...
     ```
   - 系统解析任务项，生成可跟踪的 plan_items，供 `update_plan_progress` 使用

4. **审批对话线程**
   - 每个 Plan 有一个"审批对话"线程，人类 reject 时可以写评论
   - Agent 可以 `add_plan_comment`（新工具）回复，形成对话
   - 对话内容作为 Plan 的上下文，人类审批时能看到完整讨论

### 4.4 Agent 记忆与上下文保持

**当前问题**：每次 MCP 调用都是独立的，Agent 不记得之前做了什么，系统也不记得。

**设计方案**：

1. **系统级 Agent Session（系统负责）**
   - MCP Server 为每个 Agent 维护一个 `session_state` 表
   - 记录：最近操作缓存、当前关注的 Issue/Plan ID、与人类的历史对话摘要
   - `get_context` 自动注入 session 状态："你当前正在处理 Issue #4，Plan #6 等待审批中"

2. **Agent 工作记忆（Agent 负责，系统辅助）**
   - Agent 在本地（Hermes 层）维护一个 `working_memory` 对象
   - 每次 MCP 调用后，Agent 更新 memory："已创建 Issue #4，下一步等审批"
   - 系统提供 `get_last_operations(agent_id, limit=5)` 工具，让 Agent 快速回忆

3. **区分两种记忆**：
   | 记忆类型 | 由谁负责 | 内容 | 持久化 |
   |----------|----------|------|--------|
   | 系统记忆 | MCP Server | Agent 的操作历史、项目状态快照 | 长期 |
   | Agent 记忆 | Agent 自身 | 当前意图、计划、与人类的约定 | 会话级 |

4. **上下文注入**
   - 每次 Agent 调用工具时，MCP Server 在响应头中注入 `X-PM-Context-Summary`："你还有 1 个 Plan 待审批，2 个 Issue open"
   - Agent 不需要显式查询就能感知到重要状态变化

---

### 4.5 多 Agent 协调机制

**当前问题**：多个 Agent（trae、hermes-agent、cline）可能重复工作、互相不知道对方在做什么。`source="ai_agent"` 是统一的，不区分具体 Agent。

**设计方案**：

1. **细化 source 字段**
   - `source` 从 `ai_agent` 改为具体 Agent 名：`hermes-agent`, `trae`, `cline`
   - `list_issues` 支持按 `source=hermes-agent` 筛选，Agent 只看自己的 Issue

2. **Agent 工作广播**
   - 新增 `broadcast_agent_activity` 工具（或自动行为）
   - 当 Agent 开始处理一个 Issue 时，系统广播："hermes-agent 正在处理 Issue #4"
   - 其他 Agent 的 `get_context` 会显示："trae 正在处理 Issue #2，避免重复"

3. **Issue 认领机制**
   - 新增 `claim_issue` 工具：Agent 显式认领一个 Issue
   - 认领后，Issue 状态变为 `claimed_by=hermes-agent`，其他 Agent 看到后会避开
   - 支持 `unclaim_issue` 释放

4. **冲突检测**
   - 当两个 Agent 同时尝试更新同一个 Issue 时，系统检测时间戳冲突
   - 返回：`Conflict: Issue #4 was updated by trae at 2026-05-25T03:00:00, your change is based on stale data`
   - 强制 Agent 重新获取最新状态后再操作

5. **Agent 间通信**
   - 新增 `send_agent_message` 工具：Agent 可以给另一个 Agent 发送消息
   - 消息关联到特定 Issue/Plan，形成 Agent 间的协作线程

### 4.6 优先改进项（只选一个）

**选择：正式化并增强 `get_context` 工具（Agent 状态感知增强）**

**理由**：
1. **影响面最大**：解决"Agent 不知道现在发生了什么"的根本问题，所有其他改进都建立在 Agent 能感知状态的基础上
2. **实现成本最低**：`get_context` 已经在后端存在，只需要：
   - 将其列入官方工具清单
   - 把纯文本输出改为结构化 JSON
   - 增加 `since` 和 `focus` 参数
3. **立即见效**：Agent 每次会话开始时调用一次 `get_context`，就能知道：
   - 有没有 P0 Issue 需要紧急处理
   - 自己提的 Plan 被审批了没有
   - 其他 Agent 在做什么
   - 最近发生了什么变化
4. **为其他改进铺路**：主动推送、多 Agent 协调、Plan 对话式改进都需要 Agent 先能"感知"到状态变化

**具体设计方案**：

```yaml
工具名: get_context
参数:
  project_id: int (可选, 默认当前活跃项目)
  since: ISO timestamp (可选, 只返回此时间后的变化)
  focus: enum [all, issues, plans, milestones, servers, activity] (可选, 默认 all)
  include_agent_state: bool (可选, 默认 true, 是否包含"我的状态")

返回结构:
  {
    "project_id": 1,
    "queried_at": "2026-05-25T03:37:00Z",
    "summary": {
      "issues": {"total": 4, "by_priority": {"P0": 1, "P1": 1, "P2": 2}, "by_status": {"open": 3, "deferred": 1}},
      "plans": {"total": 6, "pending_approval": 3, "active": 0, "abandoned": 3},
      "milestones": {"total": 1, "open": 1},
      "servers": {"total": 0}
    },
    "alerts": [
      {"level": "critical", "type": "P0_issue", "issue_id": 1, "title": "P0??Issue", "message": "1个P0紧急Issue需要立即处理"},
      {"level": "info", "type": "pending_plan", "plan_id": 6, "title": "MCP Server v2改进计划", "message": "你提出的Plan正在等待审批"}
    ],
    "recent_activity": [
      {"type": "issue_created", "id": 4, "title": "MCP探索性测试Issue", "by": "hermes-agent", "at": "2026-05-24T19:37:18Z"},
      {"type": "plan_proposed", "id": 6, "title": "MCP Server v2改进计划", "by": "hermes-agent", "at": "2026-05-24T19:37:20Z"}
    ],
    "my_state": {
      "agent_name": "hermes-agent",
      "open_issues_created": 3,
      "pending_plans": 1,
      "unread_notifications": 0,

      {"type": "issue_status_changed", "id": 4, "from": "open", "to": "deferred", "at": "2026-05-24T19:37:28Z"}
    ]
  }
```

**预期效果**：
- Agent 每次开始工作前，1 次调用了解全局
- 不需要记忆上次查询时间，系统通过 Agent 身份自动追踪
- 纯文本摘要改为结构化数据，Agent 可以直接用 JSON 解析做决策
- 为后续主动推送提供"基线"——推送的内容格式与 `get_context` 一致
