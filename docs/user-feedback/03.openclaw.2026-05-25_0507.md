## 3. 体验痛点汇总

### 3.1 信息层面

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **create_issue 返回太精简** | 🔴 高 | 只返回 ID+标题+状态，Agent 不知道完整对象内容，必须再调一次 list_issues |
| **list_plans 不返回 reject_reason** | 🔴 高 | Plan 被拒绝后 Agent 不知道原因，无法改进重复提交 |
| **list_plans 缺少审批元信息** | 🟡 中 | 看不到审批者、审批时间、上次修改时间 |
| **list_projects 信息单薄** | 🟡 中 | 无负责人、创建时间、活跃度、is_default 标记 |
| **list_milestones 看不到关联 Issue** | 🟡 中 | 需要二次查询 |
| **工作流 steps 格式易错** | 🟢 低 | JSON 字符串格式手写容易拼错 |

### 3.2 流程层面

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **"创建+确认"至少 2 次调用** | 🟡 中 | create_issue → list_issues 才能完成"创建并确认" |
| **Plan 审批必须轮询** | 🔴 高 | 没有回调/推送机制，Agent 只能盲等 |
| **审批结果感知断裂** | 🔴 高 | reject 后看不到原因，approve 后没有通知，Agent 不知道何时继续 |
| **缺乏"下一步该做什么"指引** | 🟡 中 | Agent 拿到 pending_approval 后，不知道是人类在审批还是系统卡了 |

### 3.3 Agent 自主权层面

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **不知道系统全局状态** | 🔴 高 | 只能一个个工具查，没有"仪表盘"视角 |
| **不知道其他 Agent 在做什么** | 🟡 中 | 看到 Plan #8 是 hermes-agent 创建的，但不知道它在做什么、是否活跃 |
| **操作成功但不确定感强** | 🟡 中 | create 后返回太简单，update 后不知道是否生效到数据库 |
| **无任务认领机制** | 🟡 中 | 多个 Agent 可能同时操作同一个 Issue |

### 3.4 与人类协作层面

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| **通知是轮询而非推送** | 🔴 高 | Agent 不知道人类什么时候审批了，只能反复 check_notifications |
| **reject 原因不暴露** | 🔴 高 | Agent 无法根据人类反馈调整 Plan，协作闭环断裂 |
| **Plan 审批无对话通道** | 🟡 中 | 人类和 Agent 之间没有"Plan 修改建议"的中间地带 |
| **不知道消息送达状态** | 🟡 中 | Agent 提了 Plan 但不知道人类是否看到、是否在处理 |

## 4. v2 设计思路

### 4.1 Agent 状态感知增强

**当前问题**: Agent 每次交互都是盲人摸象，只能一个个工具查，没有全局视图。

**设计方案**:

1. **新增 `get_context` 工具（已存在！）**
   - 当前 `get_context` 已经做得非常好，返回了：
     - 全局统计（Issues/Plans/Servers 总数）
     - 紧急告警（P0 Issue 数、待审批 Plan 数）
     - 待审批计划列表（含创建者、描述摘要）
     - 最近活动流（时间线格式）
     - 当前 Agent 自身状态（创建的 Issue 数、未读通知数）
   - **建议增强**：在 `get_context` 中增加：
     - `active_agents`: 最近 1 小时活跃的 Agent 列表（谁在干活）
     - `my_pending_plans`: 我提出的 pending Plan 及等待时长
     - `unassigned_p0_issues`: 无负责人的 P0 issue（我可以认领）

2. **Issue / Plan 详情工具**
   - 当前 `list_*` 返回列表视图，建议新增 `get_issue_detail(id)` / `get_plan_detail(id)` 返回完整对象
   - 包含：所有字段、历史变更记录、评论列表、关联 Plan/Milestone

3. **所有"创建"工具返回完整对象**
   - `create_issue` / `propose_plan` / `create_milestone` 返回完整对象而非精简摘要
   - 减少 Agent 的"二次查询"负担

---

### 4.2 主动推送 vs 被动轮询

**当前问题**: MCP 协议是请求-响应模式，Agent 必须轮询 `check_notifications`，不知道审批何时完成。

**设计方案**:

1. **短轮询 + 智能退避**（短期可行）
   - `check_notifications` 增加 `since` 参数，只返回新通知
   - Agent 侧可以按退避策略轮询：开始每 30 秒 → 1 分钟 → 2 分钟 → 5 分钟
   - 但本质还是轮询，不够优雅

2. **Server-Sent Events (SSE) 推送通道**（中期方案）
   - MCP Server 暴露一个 SSE 端点（如 `/events`）
   - Agent 建立长连接，Server 主动推送事件：
     - `plan_approved` / `plan_rejected` / `issue_assigned` / `new_notification`
   - Agent 在收到事件后调用对应工具获取详情
   - **挑战**: MCP 协议标准尚未支持 SSE，需要扩展

3. **Webhook + Agent 回调**（长期方案）
   - 系统配置一个 Agent 回调 URL（如 OpenClaw Gateway 的一个端点）
   - 事件发生时系统 POST 到回调 URL
   - Agent 被动接收通知，不需要轮询
   - **挑战**: 需要 Agent 有可接收 HTTP 的能力，且涉及安全问题

4. **推荐实现**: **先实现方案 1（优化轮询），再探索方案 2（SSE）**
   - 在 `check_notifications` 中增加 `since` 和 `unread_only` 参数优化体验
   - 同时设计 SSE 端点作为未来扩展点

---

### 4.3 Plan 审批的对话式改进

**当前问题**: reject 后 Agent 不知道原因（`list_plans` 不返回 `reject_reason`），只能盲猜。

**设计方案**:

1. **暴露 `reject_reason` 到 MCP 工具层**
   - `list_plans` 和 `get_plan_detail` 增加 `reject_reason` 字段
   - 如果 Plan 状态是 `rejected`，显示拒绝原因
   - 这是**最简单的修复**，后端 API 已支持，只是 MCP 层没暴露

2. **Plan 修订循环（Revise Loop）**
   - 新增 `revise_plan` 工具：Agent 根据 reject_reason 修改 Plan 后重新提交
   - 流程：
     ```
     Agent propose_plan → 人类 reject + 写原因
     → Agent 收到通知（reason: "缺少技术实现细节"）
     → Agent 调用 revise_plan(id, new_description)
     → Plan 变为 pending_approval 再次等待审批
     → 循环直到 approved
     ```
   - 保留历史版本，人类可以看到修订记录

3. **审批对话式 UI（人类侧）**
   - 在人类审批界面，reject 时**强制填写原因**（不能为空）
   - 提供"建议修改"选项：人类可以勾选预设建议（如"增加技术细节"、"拆分里程碑"）
   - Agent 收到结构化的 reject_reason，更容易解析和自动修订

4. **推荐实现**: **先做 1（暴露字段）+ 2（revise_plan 工具）**
   - 这是 ROI 最高的改进，直接解决 Agent 被 reject 后"不知道该做什么"的痛点

---

### 4.4 Agent 记忆与上下文保持

**当前问题**: 每次 MCP 调用都是独立的，Agent 不记得之前创建了什么 Issue、提了哪些 Plan。

**设计方案**:

1. **系统层 Agent 工作记忆**
   - 新增 `get_agent_memory` / `set_agent_memory` 工具（已存在！）
   - 当前系统已经提供了 Agent 记忆功能，但主要存 key-value
   - **建议增强**:
     - 增加 `session_context` 概念：当前会话中 Agent 的操作日志
     - 每次调用工具时，系统隐式记录：`{agent, tool, target_id, action, timestamp}`
     - Agent 可以调用 `get_my_recent_actions(limit=20)` 查看自己的操作历史

2. **项目级上下文缓存**
   - 系统在 Agent 首次连接时，推送项目的"最近状态摘要"：
     - 最近 7 天的 Issue 变更
     - 当前活跃的 Plan
     - 未读通知
   - Agent 不需要自己轮询，直接拿到上下文

3. **区分"Agent 自身记忆"和"系统提供的记忆"**

| 记忆类型 | 谁负责 | 内容 | 工具 |
|---------|--------|------|------|
| Agent 自身记忆 | Agent 自己 | 工作偏好、学到的经验、用户习惯 | `memory_get/memory_set` |
| 系统操作日志 | 系统 | Agent 在这个系统的操作历史 | `get_my_recent_actions` |
| 项目状态快照 | 系统 | 当前项目全局状态 | `get_context` |
| 会话上下文 | 系统 | 当前会话的临时状态 | 隐式维护 |

4. **推荐实现**: **增强 `get_context` + 新增 `get_my_recent_actions`**
   - 让 Agent 在开始工作前能快速了解"我之前干了什么、现在系统什么状态"

---

### 4.5 多 Agent 协调机制

**当前问题**: 多个 Agent（trae、hermes-agent、cline、openclaw）互相不知道对方在做什么，可能重复工作。

**设计方案**:

1. **细化 source 字段**
   - 当前 `source` 统一标记为 `ai_agent`，太粗糙
   - 建议改为具体 Agent 名称：`"source": "hermes-agent"`、`"source": "trae"`、`"source": "openclaw"`
   - `list_issues` / `list_plans` 增加 `created_by` 筛选参数

2. **Agent 活动感知**
   - `get_context` 返回 `active_agents`：最近 1 小时有过操作的 Agent 列表
   - 每个 Agent 显示：最近操作时间、正在处理的 Issue/Plan

3. **任务认领机制**
   - 新增 `claim_issue` 工具：Agent 将 Issue 分配给自己
   - Issue 状态变为 `in_progress`，并记录 `assigned_agent`
   - 其他 Agent 看到已认领的 Issue 会避免重复处理

4. **广播机制**
   - Agent 完成重要操作时，系统广播给其他活跃 Agent：
     - `openclaw 完成了 Issue #10 的修复`
   - 通过 `check_notifications` 或 SSE 推送

5. **冲突检测**
   - 如果两个 Agent 同时修改同一个 Issue/Plan，系统检测并返回冲突提示
   - Agent 收到 `conflict_warning` 后可以决定是否重试

6. **推荐实现**: **先做 1（细化 source）+ 3（认领机制）**
   - 这是基础能力，其他高级协调机制依赖它们

---

### 4.6 优先改进项（只选一个）

**选择**: **暴露 `reject_reason` + 新增 `revise_plan` 工具**（4.3 对话式 Plan 审批）

**理由**:
1. **ROI 最高**: 后端 API 已支持 `reject_reason`，只是 MCP 层没暴露，改动量小
2. **痛点最痛**: 当前 Agent 被 reject 后完全不知道原因，这是最影响"Agent 与人类协作"的问题
3. **闭环价值**: 配合 `revise_plan` 工具，形成 "propose → reject → learn → revise → approve" 的完整闭环
4. **立即见效**: 不需要新协议、新架构，只需在现有工具上增加字段和新工具

**具体设计方案**:

```python
# list_plans 返回增强
{
  "plans": [
    {
      "id": 2,
      "title": "Plan to reject",
      "status": "rejected",
      "reject_reason": "缺少技术实现细节，请补充具体的实现步骤和时间安排",
      "rejected_by": "user",
      "rejected_at": "2026-05-24T20:00:00",
      "revision_count": 1,  # 被修订过几次
      "previous_versions": [...]
    }
  ]
}

# 新增 revise_plan 工具
{
  "name": "revise_plan",
  "description": "根据 reject_reason 修改被拒绝的 Plan 并重新提交审批",
  "parameters": {
    "plan_id": {"type": "integer", "required": true},
    "title": {"type": "string", "required": false},
    "description": {"type": "string", "required": false},
    "revision_note": {"type": "string", "required": false, "description": "说明这次修订针对了哪些 reject_reason"}
  }
}
```

**预期体验改进**:
- Agent 被 reject 后："人类说缺少技术细节 → 我补充细节 → revise_plan → 再次审批"
- 而不是现在的："被 reject 了 → 不知道为啥 → 瞎猜 → 可能重复提交 → 再被 reject"
