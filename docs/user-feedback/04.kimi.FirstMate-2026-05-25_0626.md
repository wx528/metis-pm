## 2. 工具探索体验

### 2.1 全局概览 (`get_context`)

**调用结果**：
```
=== 项目全局概览 ===
Issues: 0 total | P0: 0 | P1: 0 | Open: 0 | In Progress: 0 | Deferred: 0 | AI Agent: 0
Plans: 0 total | Pending Approval: 0 | Active: 0 | Abandoned: 0
```

**体验感受**：

- **严重问题**：`get_context` 返回的统计数字全部为 0，但实际数据库中有 13 个 Issue、10 个 Plan。这是一个明显的统计 Bug——全局概览没有正确聚合数据。
- **待审批 Plan 列表**：虽然统计为 0，但下方"待审批计划"区域正确列出了 4 个待审批 Plan（#1, #2, #5, #6）。这部分是准确的。
- **P0 紧急告警**：统计为 0，但实际存在 P0 Issue（#1）。如果这是生产环境，大副会漏掉紧急问题。
- **活跃 Agent 列表**：缺失。get_context 没有显示当前有哪些 Agent 在线或最近活跃。
- **无负责人 P0 Issue**：缺失。没有专门的区域提示"需要立即分配的高优先级 Issue"。
- **最近活动**：显示了 10 条最近活动记录，但信息过于简略（只有 `[issue#6] status_changed by first-mate`），没有显示变更前后的值。

**总体评价**：get_context 的"待审批计划"和"最近活动"有价值，但统计数字完全不可信。作为大副，我不能依赖这个概览做决策，必须手动调用 list_issues 和 list_pending_plans 交叉验证。

### 2.2 Plan 审批流程（核心体验）

#### 2.2.1 查看待审批 Plan (`list_pending_plans`)

**调用结果**：返回 4 个待审批 Plan，包含 ID、标题、描述（完整未截断）、提议者、创建时间。

**体验**：
- ✅ 信息足够做初步筛选：能看到提议者（ai_agent / user / trae / openclaw）和描述
- ✅ 描述未被截断，Plan #6 的长描述完整显示
- ⚠️ 缺少关键信息：没有显示 Plan 关联的 Issue、没有提议者的历史表现、没有项目资源占用情况
- ⚠️ 无法判断 Plan 的紧急程度：没有优先级字段，只能按创建时间排序

#### 2.2.2 查看 Plan 详情 (`get_plan_detail`)

**测试案例**：
- Plan #6（待审批）：显示提议者 ai_agent、项目 #1、描述、创建/更新时间
- Plan #8（已拒绝）：显示拒绝原因 "Scope too broad, please split into smaller plans"
- Plan #7（已审批）：显示审批者 first-mate 和审批时间

**体验**：
- ✅ 审批信息清晰：谁审批的、什么时候审批的，一目了然
- ✅ 拒绝原因可见：已拒绝 Plan 的详情页明确显示 reject_reason
- ⚠️ 缺少进度项列表：get_plan_detail 没有显示 Plan 包含哪些任务/进度项
- ⚠️ 缺少历史版本：如果 Plan 被拒绝后修改重新提交，无法看出这是第几版
- ⚠️ 缺少关联 Issue：无法直接看到该 Plan 是为了解决哪些 Issue

#### 2.2.3 审批通过 (`approve_plan`)

**操作**：approve_plan(plan_id=5) → Plan #5 APPROVED ✅

**体验**：
- ✅ 操作极其简洁：一个参数（plan_id），瞬间返回
- ✅ 返回信息完整：包含标题、新状态（active）、审批者、审批时间
- ✅ 状态变化明确：从 pending_approval → active

#### 2.2.4 拒绝 Plan (`reject_plan`)

**测试 1：不填 reason**
- 结果：`Error: 拒绝 Plan 必须填写原因，帮助 Agent 理解问题并改进`
- 体验：错误提示清晰、友好，明确告知必须填原因

**测试 2：填写 reason**
- 操作：reject_plan(plan_id=2, reason="描述过于模糊...")
- 结果：Plan #2 REJECTED ❌，返回包含完整拒绝原因
- 体验：拒绝操作顺畅，返回信息确认了拒绝原因

**体验**：
- ✅ 强制填 reason 的设计非常好，避免了大副随意拒绝
- ✅ 拒绝原因会完整返回，工人应该能从通知中看到
- ⚠️ 但 check_notifications 始终返回 No notifications，无法验证工人是否真的收到了拒绝通知

#### 2.2.5 审批决策体验

**整体流程**：
1. get_context → 发现有待审批 Plan（但统计为 0，不可靠）
2. list_pending_plans → 看到 4 个待审批 Plan 的摘要
3. get_plan_detail → 查看具体 Plan 的描述和背景
4. approve_plan / reject_plan → 做出决策

**痛点**：
- 从"发现"到"决策"需要 3 步，流程本身合理
- 但决策信息严重不足：我不知道提议者 ai_agent 之前完成的 Plan 质量如何，不知道这个项目当前有多少 Active Plan，不知道资源是否足够
- **"想批但不敢批"的时刻**：Plan #6 "MCP Server v2改进计划"描述宏大，但我看不到它关联哪些 Issue、需要多少资源、ai_agent 是否有能力执行。最终只能基于描述"看起来合理"就批准了——这不是数据驱动的决策。

### 2.3 Issue 分配与管理

#### 2.3.1 查询 Issue (`list_issues`)

**测试的筛选条件**：
- `status=open`：返回 7 个 open Issue
- `priority=P0`：返回 1 个 P0 Issue（#1）
- `assignee=hermes-agent`：返回 1 个 Issue（#8）
- `created_by=hermes-agent`：返回 2 个 Issue
- `sort_by=priority_asc`：按 P0→P1→P2 排序，13 个 Issue 全部列出
- `sort_by=updated_at_desc`：按最近更新排序

**体验**：
- ✅ 筛选条件实用：能快速找到"未分配的 Issue"、"某个 Agent 的 Issue"
- ✅ 排序功能正常：priority_asc 和 updated_at_desc 都符合预期
- ⚠️ 缺少"无负责人"筛选：不能直接用 `assignee=null` 筛选，只能通过返回结果中的"负责人: 未分配"肉眼识别
- ⚠️ 缺少多条件组合筛选：不能同时筛选 `status=open AND priority=P0`

#### 2.3.2 查看 Issue 详情 (`get_issue_detail`)

**测试案例**：
- Issue #8（有评论）：显示评论列表，包含评论 ID、作者、内容
- Issue #10（有推迟）：显示"推迟到: milestone #1"和推迟原因
- Issue #1（P0）：显示完整字段

**体验**：
- ✅ 评论列表完整显示，包含作者和内容
- ✅ 推迟信息清晰可读（里程碑 + 原因）
- ✅ 里程碑关联显示为"里程碑: #无"或"里程碑: #1"
- ⚠️ 评论没有区分"管理评论"和"普通评论"：大副添加的 comment #7 和工人添加的 comment #3 在 UI 上完全一致

#### 2.3.3 分配 Issue (`assign_issue`)

**操作**：assign_issue(issue_id=1, assignee='hermes-agent')

**体验**：
- ✅ 操作简洁：issue_id + assignee 两个参数
- ✅ 返回确认：显示新负责人
- ⚠️ **assign_issue 不改状态**：分配后 Issue 仍然是 open，需要额外调用 update_issue_status 设为 in_progress
- ⚠️ **两步操作应该合并**：作为大副，我分配任务的目的就是让它开始执行，99% 的情况下我需要同时改 assignee 和 status。当前设计迫使我调用两次工具。

#### 2.3.4 调整优先级 (`set_issue_priority`)

**测试**：P0 → P3 → P0

**体验**：
- ✅ 即时生效：每次调整都立即返回新优先级
- ✅ 无限制：可以从 P0 直接降到 P3，也可以升回来
- ✅ 返回确认：明确显示新优先级

#### 2.3.5 更新状态 (`update_issue_status`)

**测试**：open → in_progress → closed

**体验**：
- ✅ 状态转换无限制：可以从 open 直接跳到 closed
- ✅ 返回确认：明确显示新状态
- ⚠️ 状态可选值不清晰：工具定义中没有明确列出所有可选状态值，需要试错或看文档
- ⚠️ 缺少状态转换校验：例如是否允许 closed → open？实际测试发现可以任意跳转

#### 2.3.6 添加管理评论 (`add_issue_comment`)

**操作**：add_issue_comment(issue_id=8, content="【大副审批意见】...")

**体验**：
- ✅ 作者自动标记为 first-mate
- ✅ 返回确认：显示 comment_id
- ⚠️ **无法区分管理评论和普通评论**：评论列表中，大副的评论和工人的评论在格式上完全一致，没有 visual distinction
- ⚠️ 没有"评论类型"字段：无法标记为"审批意见"、"指导说明"、"阻塞升级"等不同类型

### 2.7 权限边界测试（RBAC 验证）

## 3. 体验痛点汇总

### 3.1 管理决策层面

| 痛点 | 严重程度 | 说明 |
|------|----------|------|
| 审批 Plan 时信息不足 | 🔴 高 | 看不到提议者历史完成率、Plan 关联 Issue、资源需求，只能凭描述主观判断 |
| 不了解 Agent 工作负载 | 🔴 高 | get_agent_activities 只显示历史，不显示当前 workload。分配 Issue 时不知道谁忙谁闲 |
| 无法快速判断"最需要关注的 Issue" | 🟡 中 | 虽然有 P0/P1/P2 优先级，但 get_context 统计为 0，需要手动 list_issues 筛选 |
| 分配后无法追踪执行 | 🟡 中 | 分配 Issue 后，没有机制追踪 Agent 是否开始执行、进度如何 |

### 3.2 信息层面

| 痛点 | 严重程度 | 说明 |
|------|----------|------|
| get_context 统计完全错误 | 🔴 高 | Issues: 0 total / P0: 0 / Open: 0，全部与实际不符 |
| 缺少"无负责人 P0 Issue"告警 | 🔴 高 | get_context 没有专门提示需要立即分配的高优先级 Issue |
| 里程碑统计错误 | 🟡 中 | milestone #1 显示 deferred: 0，但实际有 Issue defer 到它 |
| 活动记录变更详情被截断 | 🟡 中 | 看不到状态变更前后的具体值 |
| 评论无类型区分 | 🟡 中 | 管理评论和普通评论混在一起 |
| 项目统计信息太少 | 🟢 低 | 只有 issue/plan/milestone 总数，没有健康度指标 |

### 3.3 流程层面

| 痛点 | 严重程度 | 说明 |
|------|----------|------|
| 分配 Issue 需要两次调用 | 🔴 高 | assign_issue + update_issue_status，99% 场景需要合并 |
| 从"发现待审批"到"完成审批"需要 3 步 | 🟡 中 | get_context → list_pending_plans → get_plan_detail → approve/reject，步骤合理但信息不足 |
| 无法追踪已审批 Plan 的执行 | 🔴 高 | 审批后 Plan 变为 active，但大副没有工具查看 Plan 的进度更新 |
| 通知机制失效 | 🔴 高 | check_notifications 始终返回空，大副只能主动轮询 |

### 3.4 大副 vs 工人协作层面

| 痛点 | 严重程度 | 说明 |
|------|----------|------|
| 通知机制不可靠 | 🔴 高 | 工人提交 Plan 后，大副无法通过通知感知，必须主动轮询 |
| 拒绝后不知道工人是否改进 | 🔴 高 | Plan #2 被拒绝后，工人可能重新提交，但大副无法区分"新 Plan"和"修改后的旧 Plan" |
| 缺少"管理标签"机制 | 🟡 中 | 大副无法给 Issue 打标签指导工人（如"需要拆分"、"阻塞：等待外部依赖"） |
| 职责边界基本清晰 | 🟢 低 | 创建/提议是工人的事，审批/分配是大副的事，边界明确 |

### 3.5 大副自主权层面

| 痛点 | 严重程度 | 说明 |
|------|----------|------|

### 4.5 大副权限与安全

**当前权限矩阵（已实现）**：

| 操作 | admin | agent (工人) | mate (大副) |
|------|-------|-------------|-------------|
| 创建 Issue/Plan/项目/里程碑 | ✅ | ✅ | ❌ 403 |
| 审批/拒绝 Plan | ✅ | ❌ 403 | ✅ |
| 更新 Plan 进度 | ✅ | ✅ | ❌ 403 |
| 工作流写操作 | ✅ | ✅ | ❌ 403 |
| 工作流审批恢复 | ✅ | ❌ 403 | ✅ |
| Agent 记忆 | ✅ | ✅ | ❌ 403 |
| 删除操作 | ✅ | ❌ 403 | ❌ 403 |
| 读取（列表/详情） | ✅ | ✅ | ✅ |
| 更新 Issue（状态/优先级/assignee） | ✅ | ✅ | ✅ |

**测试体验后的调整建议**：

#### 4.5.1 需要调整的权限

| 操作 | 当前 | 建议 | 理由 |
|------|------|------|------|
| 大副关闭任意 Issue | ✅ | ✅ 保留 | 大副需要清理已完成或无效的 Issue |
| 大副修改任意 Issue 优先级 | ✅ | ✅ 保留 | 大副需要根据项目全局调整优先级 |
| 大副更新 Plan 进度 | ❌ 403 | 🟡 只读 | 大副应该能**查看** Plan 进度，但不应修改（工人负责执行） |
| 大副查看 Agent 记忆 | ❌ 403 | 🟡 考虑开放摘要版 | 大副需要了解 Agent 的上下文以做分配决策，但不应查看完整记忆 |
| 大副删除 Issue | ❌ 403 | ❌ 保持禁止 | 删除应该由 admin 或创建者执行 |

#### 4.5.2 新增权限控制

- **大副操作审计日志**：所有大副的审批、拒绝、分配、优先级调整操作都应该记录审计日志，admin 可查询
- **大副操作确认机制**：对于高风险操作（如批量关闭 Issue、降级 P0 优先级），增加确认提示或二次确认
- **时间窗口限制**：例如已关闭超过 7 天的 Issue，大副不能重新打开（防止误操作）

#### 4.5.3 细化 Issue 更新权限

当前 `update_issue_status` 对所有角色开放，建议细化：

| 状态转换 | 工人 | 大副 | 说明 |
|----------|------|------|------|
| open → in_progress | ✅（自己负责的） | ✅（任意） | |
| in_progress → review | ✅（自己负责的） | ✅（任意） | |
| review → closed | ❌ | ✅ | 只有大副能最终关闭（验收） |
| any → deferred | ✅ | ✅ | |
| closed → open | ❌ | ✅ | 大副可以 reopen |

### 4.6 优先改进项（只选一个）

**选择：修复并增强 `get_context`（大副工作台）**

**理由**：
1. **影响最大**：get_context 是大副的"首页"，每次打开都会调用。如果首页数据错误，大副对整个系统的信任度会崩塌。
2. **阻塞其他功能**：当前统计为 0 导致大副无法依赖概览，被迫手动调用多个工具交叉验证，效率极低。
3. **管理决策的基础**：没有准确的全局概览，所有审批、分配决策都是盲目的。

**具体设计方案**：
