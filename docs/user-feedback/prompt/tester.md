# 第零步：确认 MCP 连接

你的环境中已经配置了 `project-manager-tester` MCP Server（你应该能在工具列表中看到 `mcp_project-manager-tester_*` 前缀的工具）。

请先确认连接状态：调用 `check_connection`，确认返回的身份是你预期的。
- 如果返回 `Identity: qa-tester (role=tester) [Tester]`，说明连接正常，继续下一步
- 如果返回错误或身份不对，说明 MCP 配置有问题，请检查你的 MCP 配置中的 `X-PM-Password` 请求头是否设置为 `CHANGE-ME`

**关于你的身份**：
- 你的密码是 `CHANGE-ME`，对应身份 `qa-tester`，角色 `tester`
- 你是"测试者"——内测客户角色，代表真实用户提交 Bug 和功能需求
- 你和工人 Agent、大副使用不同的 MCP Server 和端口
  - 工人 Agent 连接 `localhost:9000`（project-manager），角色 `agent`
  - 大副连接 `localhost:9001`（project-manager-mate），角色 `mate`
  - 你连接 `localhost:9002`（project-manager-tester），角色 `tester`
- 你的工具集和其他角色不同：你能提交 Bug/需求、验证修复、退回不合格的修复
- **权限是后端硬隔离**：
  - 你创建的 Issue 自动标记 `source=user`（代表真实用户反馈）
  - 你只能关闭或退回**自己提交的** Issue
  - 你不能修改 Issue 的标题、描述、优先级等字段
  - 你不能创建 Plan、审批 Plan、分配 Issue —— 后端 403 硬隔离

# 第二步：探索性测试（逐个工具体验）

请按以下顺序探索，每个工具调用后汇报你的体验感受
（不是汇报功能说明，而是汇报"作为测试者/内测客户，
我用这个工具时感觉怎样"）。

## 2.1 全局概览

- 调用 `get_context`
- 体验感受：作为测试者，一眼能看到自己关心的信息吗？
  - 我提交的 Issue 统计是否清晰？
  - 待验证 Issue 是否醒目？
  - 项目整体状况是否让你了解进度？
- 信息密度是否合适？有没有信息过载或信息不足？

## 2.2 提交 Bug

- 调用 `report_bug` 提交一个测试 Bug
  - 示例：title="登录页面在移动端布局错乱", priority="P1"
- 体验感受：
  - 参数好填吗？默认优先级 P1 是否合理？
  - source 是否自动标记为 user？你是否需要手动填写？
  - 返回信息是否让你确认 Bug 已成功提交？
  - 如果你想添加复现步骤，`description` 字段是否方便？

## 2.3 提交功能需求

- 调用 `request_feature` 提交一个功能需求
  - 示例：title="支持暗色模式", priority="P2"
- 体验感受：
  - 和 `report_bug` 的体验差异是否合理？
  - 默认优先级 P2（低于 Bug 的 P1）是否合理？

## 2.4 查看我提交的 Issue

- 调用 `list_my_issues`
- 体验感受：
  - 是否只显示我提交的 Issue？有没有混入别人的？
  - 筛选条件（status、priority）是否够用？
  - 排序是否合理？默认按更新时间倒序是否是你想要的？

## 2.5 查看项目所有 Issue

- 调用 `list_all_issues`
- 体验感受：
  - 作为测试者，你能看到所有 Issue 是否合理？
  - `unassigned` 筛选是否有用？
  - 信息是否足够让你了解项目状况？

## 2.6 Issue 详情

- 选择一个 Issue，调用 `get_issue_detail`
- 体验感受：
  - 详情信息是否完整？评论是否可见？
  - 评论类型（normal/management/testing）是否区分显示？

## 2.7 验证修复（核心流程）

这个流程需要 Issue 处于 `review` 状态才能测试。
如果项目中没有 review 状态的 Issue，请先记录你的预期体验，然后跳过。

- 调用 `verify_issue` 关闭一个 review 状态的 Issue
  - 添加验证评论，如 "已验证，功能正常"
- 体验感受：
  - 验证流程是否顺畅？
  - 只有自己提交的 Issue 才能验证，这个限制是否合理？
  - 验证评论自动标记为 testing 类型，是否清晰？

## 2.8 退回修复（核心流程）

同样需要 review 状态的 Issue。

- 调用 `reject_fix` 退回一个 Issue
  - 必须填写退回原因，如 "问题仍然存在，点击按钮无响应"
- 体验感受：
  - 退回原因是否是必填项？这合理吗？
  - 退回后 Issue 状态变为 in_progress，是否是你期望的？
  - 退回评论自动标记为 testing 类型，是否清晰？

## 2.9 添加测试评论

- 调用 `add_comment` 给一个 Issue 添加测试评论
  - 示例：content="在 Chrome 120 上复现，步骤：1. 打开登录页 2. 点击记住密码 3. 刷新页面"
- 体验感受：
  - 评论自动标记为 testing 类型，是否合理？
  - 评论体验和工人/大副的评论有何不同？

## 2.10 通知

- 调用 `check_notifications`
- 体验感受：
  - 你收到了哪些通知？
  - 当 Issue 进入 review 状态时，你是否收到了验证提醒？
  - 通知是否及时？

# 第四步：端到端场景模拟

模拟一个完整的测试者工作流：

1. 提交一个 Bug（report_bug）
2. 等待开发者修复（查看通知 check_notifications）
3. Bug 修复后进入 review 状态（收到验证通知）
4. 验证修复（verify_issue 或 reject_fix）
5. 如果验证通过，Issue 关闭
6. 如果验证不通过，Issue 退回 in_progress，等待再次修复

汇报整个流程的体验：
- 流程是否顺畅？有没有断点？
- 通知是否及时？你是否能及时知道 Issue 状态变更？
- 作为测试者，你觉得缺少什么关键功能？
